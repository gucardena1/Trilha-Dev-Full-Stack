7. Vue.js

Integrando Vue com uma API

Como consumir uma API REST de dentro de um componente, tratar carregamento e erro de forma correta, e o que de fato é CORS.

Até aqui, todos os dados que você usou nas lições viviam dentro do próprio componente ou de uma store local, criados na hora e sem depender de nada externo. Uma aplicação real, porém, quase sempre precisa buscar e enviar dados para um servidor — um backend em Node.js, PHP, Python, o que for, expondo uma API REST. Esta lição fecha a trilha de Vue conectando as duas pontas: o frontend que você já sabe construir e o backend que alimenta essa interface com dados de verdade.

Buscando dados com fetch dentro de um componente

O padrão mais comum é disparar a requisição assim que o componente é criado, usando o hook de ciclo de vida onMounted, e guardar o resultado em uma variável reativa: 

<script setup>
import { ref, onMounted } from 'vue'

const produtos = ref([])
const carregando = ref(true)
const erro = ref(null)

onMounted(async () => {
  try {
    const resposta = await fetch('https://api.minhaloja.com/produtos')

    if (!resposta.ok) {
      throw new Error(`Erro do servidor: ${resposta.status}`)
    }

    produtos.value = await resposta.json()
  } catch (e) {
    erro.value = 'Não foi possível carregar os produtos.'
    console.error(e)
  } finally {
    carregando.value = false
  }
})
</script>

<template>
  <p v-if="carregando">Carregando produtos...</p>
  <p v-else-if="erro">{{ erro }}</p>
  <ul v-else>
    <li v-for="produto in produtos" :key="produto.id">
      {{ produto.nome }} — R$ {{ produto.preco }}
    </li>
  </ul>
</template>

Repare na estrutura das três variáveis reativas: carregando, erro e produtos. Isso não é só um detalhe estético — é o padrão fundamental de qualquer chamada assíncrona numa interface de usuário. Toda requisição a um servidor tem, no mínimo, três estados possíveis pelos quais ela passa: está em andamento, terminou com sucesso, ou terminou com erro. Se o seu componente só souber lidar com o "sucesso", o usuário vai ficar olhando para uma tela em branco (ou pior, quebrada) toda vez que a rede estiver lenta ou o servidor falhar.

Atenção Um erro muito comum é esquecer de verificar resposta.ok. Diferente do que muita gente espera, o fetch não lança um erro automaticamente quando o servidor responde com um status de erro, como 404 ou 500 — ele só lança erro em falhas de rede (sem internet, servidor fora do ar). Se você não checar resposta.ok manualmente e tentar usar resposta.json() direto, seu código pode "funcionar sem erro" mesmo quando o servidor devolveu uma página de erro no lugar dos dados esperados.

Usando axios como alternativa

O fetch é nativo do navegador e não precisa de instalação, mas a biblioteca axios é uma alternativa muito popular que simplifica alguns detalhes — ela já lança erro automaticamente em respostas de status de erro, e já converte a resposta para JSON sem um passo extra: 

npm install axios
<script setup>
import { ref, onMounted } from 'vue'
import axios from 'axios'

const produtos = ref([])
const carregando = ref(true)
const erro = ref(null)

onMounted(async () => {
  try {
    const resposta = await axios.get('https://api.minhaloja.com/produtos')
    produtos.value = resposta.data // axios já entrega os dados prontos em .data
  } catch (e) {
    erro.value = 'Não foi possível carregar os produtos.'
    console.error(e)
  } finally {
    carregando.value = false
  }
})
</script>

A lógica de carregando/erro/produtos é idêntica — a diferença entre fetch e axios é só na forma de fazer a chamada e tratar o erro, não no padrão de estados que você expõe para o template.

Extraindo a lógica de busca para um composable

Como você viu na lição de Composition API, sempre que um padrão se repete entre componentes, vale a pena extraí-lo. Buscar dados de uma API é um dos casos mais comuns disso: 

// useFetch.js
import { ref } from 'vue'

export function useFetch(url) {
  const dados = ref(null)
  const carregando = ref(true)
  const erro = ref(null)

  fetch(url)
    .then(resposta => {
      if (!resposta.ok) throw new Error(`Erro: ${resposta.status}`)
      return resposta.json()
    })
    .then(json => { dados.value = json })
    .catch(e => { erro.value = e.message })
    .finally(() => { carregando.value = false })

  return { dados, carregando, erro }
}
<script setup>
import { useFetch } from './useFetch.js'

const { dados: produtos, carregando, erro } = useFetch('https://api.minhaloja.com/produtos')
</script>

Note o uso de { dados: produtos, ... } na desestruturação — isso apenas renomeia dados para produtos no componente que consome o composable, sem afetar a reatividade, porque estamos desestruturando refs (que continuam reativos fora do objeto), e não um reactive().

O que é CORS, de forma simples

Em algum momento, ao tentar consumir uma API a partir do seu frontend Vue, você vai se deparar com um erro no console mencionando "CORS" — geralmente algo como "blocked by CORS policy". Isso não é um bug no seu código Vue; é uma regra de segurança do próprio navegador.

Analogia Imagine um prédio comercial com um porteiro rigoroso. Você (o navegador) mora nesse prédio (o site meusite.com) e quer entregar uma encomenda num outro prédio, o escritório de uma API que está em api.outraempresa.com. O porteiro do outro prédio (o servidor da API) tem uma lista de "endereços de onde aceito visitas" — se o seu prédio não estiver nessa lista, o porteiro simplesmente recusa a entrega na entrada, mesmo que a encomenda em si esteja perfeita. CORS (Cross-Origin Resource Sharing) é exatamente essa lista de permissões: o servidor da API precisa dizer explicitamente, através de um cabeçalho HTTP chamado Access-Control-Allow-Origin, quais "endereços" (origens, isto é, domínios) têm permissão para fazer requisições a ele a partir do navegador. Se o seu site não estiver nessa lista, o navegador bloqueia a resposta antes mesmo dela chegar até o seu código Vue — por segurança, para impedir que sites maliciosos façam requisições escondidas em nome do usuário para APIs que ele nem sabe que existem.

Um ponto importante: o bloqueio de CORS acontece no navegador, não no seu código. Se você tentar fazer a mesma requisição a partir de um servidor (Node.js, por exemplo, sem navegador envolvido), ela funciona normalmente, porque a política de CORS é uma regra específica de segurança de navegadores web, não do protocolo HTTP em si. Por isso, um erro de CORS não se resolve mudando algo no Vue — a solução é sempre do lado do servidor da API, que precisa configurar os cabeçalhos corretos autorizando o domínio do seu frontend.

Dica Durante o desenvolvimento local, uma solução comum e prática é configurar um "proxy" no seu servidor de desenvolvimento do Vite, que redireciona as chamadas da sua aplicação para a API por trás dos panos, como se ambas estivessem na mesma origem. Isso evita lidar com CORS enquanto você desenvolve, mas não substitui a configuração correta de CORS no servidor quando a aplicação for para produção.

Enviando dados: POST, PUT e DELETE

O mesmo padrão de carregando/erro/sucesso se aplica a operações de escrita, só que geralmente disparadas por uma ação do usuário (like um clique) em vez de onMounted: 

<script setup>
import { ref } from 'vue'

const enviando = ref(false)
const erro = ref(null)

async function criarProduto(produto) {
  enviando.value = true
  erro.value = null

  try {
    const resposta = await fetch('https://api.minhaloja.com/produtos', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(produto)
    })

    if (!resposta.ok) throw new Error('Falha ao criar produto')

    return await resposta.json()
  } catch (e) {
    erro.value = e.message
  } finally {
    enviando.value = false
  }
}
</script>

Com isso, você já tem o essencial para ligar qualquer tela Vue a um backend real: buscar dados com tratamento adequado de carregamento e erro, extrair essa lógica em composables reutilizáveis, entender por que erros de CORS aparecem (e que a correção fica do lado do servidor), e enviar dados de volta ao servidor a partir de ações do usuário. A partir daqui, o próximo passo natural é aprofundar no backend em si — que é exatamente o que as próximas trilhas desta plataforma cobrem.

Resumo

  • Toda chamada assíncrona a uma API deve tratar três estados na interface: carregando, sucesso e erro.
  • fetch não lança erro automaticamente em respostas com status de erro — é preciso checar resposta.ok manualmente; axios já faz isso por padrão.
  • A lógica de busca de dados pode ser extraída para um composable reutilizável (useFetch), seguindo o mesmo padrão de outras lições.
  • CORS é uma política de segurança do navegador: o servidor da API precisa autorizar explicitamente quais domínios podem chamá-lo; a correção sempre acontece no backend, não no Vue.
  • Operações de escrita (POST/PUT/DELETE) seguem o mesmo padrão de estados de uma busca, geralmente disparadas por uma ação do usuário em vez de onMounted.
