3. JavaScript

Closures, this e padrões avançados

Os conceitos que separam "sei usar JavaScript" de "entendo como JavaScript funciona por dentro" — e alguns padrões de código que você vai encontrar em qualquer projeto profissional.

Closures: a mochila que a função carrega

Uma closure acontece quando uma função "lembra" das variáveis do lugar onde ela foi criada, mesmo depois que esse lugar já terminou de executar. Parece abstrato, mas você provavelmente já usou closures sem perceber, toda vez que criou uma função dentro de outra função.

Analogia Imagine que uma função é uma pessoa saindo de casa para uma viagem longa. Antes de sair, ela arruma uma mochila com tudo que vai precisar: as variáveis que existiam no ambiente onde ela nasceu. Não importa para onde essa pessoa vá depois (para onde essa função seja chamada), ela sempre carrega a mochila com ela — continua tendo acesso ao que colocou lá dentro, mesmo longe de casa. 
function criarContador() {
  let contagem = 0; // essa variável vai para a "mochila"

  return function () {
    contagem = contagem + 1;
    return contagem;
  };
}

const contador1 = criarContador();
console.log(contador1()); // 1
console.log(contador1()); // 2
console.log(contador1()); // 3

const contador2 = criarContador(); // uma mochila NOVA e independente
console.log(contador2()); // 1

criarContador já terminou de executar há muito tempo quando chamamos contador1() pela primeira vez. Ainda assim, a função interna continua enxergando e alterando contagem, porque ela "guardou" essa variável na sua mochila (closure) no momento em que foi criada. Repare também que contador1 e contador2 têm mochilas separadas — cada chamada de criarContador() cria um novo ambiente independente.

Isso é extremamente útil para criar estado privado: variáveis que só aquela função específica consegue acessar ou alterar, protegidas do resto do código.

Pegadinha comum Lembra do problema do var em loops, na lição anterior? Ele acontece exatamente por causa de closures: como var não cria uma variável nova a cada volta do loop, todas as funções criadas dentro dele acabam compartilhando a mesma mochila, com a mesma variável — e por isso todas "veem" o valor final dela. Usar let resolve porque ele cria uma mochila nova a cada iteração.

O que é this e por que ele muda

this é uma palavra especial em JavaScript que se refere a "quem está chamando a função" — mas seu valor não é fixo: ele depende de como a função foi chamada, não de onde ela foi escrita. Essa é a fonte de mais confusão para quem está aprendendo JS.

Analogia Pense em this como a palavra "eu" numa carta. Se a Ana escreve "eu gosto de café" e entrega a carta para o Bruno ler em voz alta, "eu" não passa a significar Bruno — mas em JavaScript, de certa forma, é como se acontecesse isso: "this" muda de significado dependendo de quem está "lendo em voz alta" (chamando) a função naquele momento. 
const pessoa = {
  nome: "Marina",
  saudar: function () {
    console.log("Olá, eu sou " + this.nome);
  }
};

pessoa.saudar(); // "Olá, eu sou Marina" — this = pessoa, porque pessoa.saudar() chamou

const funcaoSolta = pessoa.saudar;
funcaoSolta(); // "Olá, eu sou undefined" — this mudou! Agora não há um "dono" claro

Repare: é a mesma função nos dois casos. O que muda é a forma como ela foi chamada. Quando chamada como pessoa.saudar(), o "dono" da chamada é pessoa, então this aponta para pessoa. Quando chamada solta, sem um objeto na frente, this perde essa referência.

Arrow functions e this: a diferença mais importante

Arrow functions não têm o seu próprio this — elas "herdam" o this do lugar onde foram escritas (o escopo ao redor), e nunca mudam esse valor, não importa como forem chamadas. Isso resolve um problema clássico: 

const relogio = {
  hora: 10,
  iniciar: function () {
    // "function" normal: this muda dentro do setInterval,
    // deixaria de apontar para "relogio"
    setInterval(function () {
      // this.hora aqui seria undefined
    }, 1000);

    // arrow function: herda o "this" de fora (de iniciar),
    // que é o relogio. Continua funcionando corretamente.
    setInterval(() => {
      this.hora = this.hora + 1;
      console.log(this.hora);
    }, 1000);
  }
};
Dica Regra prática que resolve 90% dos casos: use arrow functions para callbacks (funções passadas para outra função, como dentro de setInterval, .then() ou addEventListener) quando você precisar que this continue apontando para o objeto ao redor. Use funções normais quando você quer que this seja definido por quem chama a função, como em métodos de objetos.

Protótipos: como os objetos "herdam" comportamento

Em JavaScript, quase todo objeto tem um "objeto de apoio" por trás dele, chamado de protótipo, de onde ele pode usar propriedades e métodos emprestados. Quando você chama array.map(...), por exemplo, o array em si não tem um método map "colado" nele — ele existe no protótipo compartilhado por todos os arrays, e o JavaScript sobe essa cadeia (chamada de "prototype chain") procurando o método até encontrar. 

function Animal(nome) {
  this.nome = nome;
}

// Adicionando um método ao protótipo: TODO animal criado
// com "new Animal(...)" vai poder usar esse método
Animal.prototype.emitirSom = function () {
  console.log(this.nome + " faz um som.");
};

const cachorro = new Animal("Rex");
cachorro.emitirSom(); // "Rex faz um som."

A sintaxe de class, que existe desde o ES6, é hoje a forma preferida de escrever isso — mas por baixo dos panos ela continua usando protótipos: 

class AnimalClasse {
  constructor(nome) {
    this.nome = nome;
  }

  emitirSom() {
    console.log(this.nome + " faz um som.");
  }
}

const gato = new AnimalClasse("Miau");
gato.emitirSom(); // "Miau faz um som."

Não é preciso dominar protótipos em profundidade para trabalhar com JavaScript no dia a dia — o importante aqui é entender que, quando você usa class, por trás existe esse mecanismo de "cadeia de protótipos" que permite objetos compartilharem comportamento.

Padrões comuns: debounce e throttle

Alguns eventos disparam com muita frequência — scroll, resize da janela, ou input enquanto o usuário digita. Se você rodar uma operação pesada (como uma chamada de API) a cada disparo, pode travar a página ou gerar dezenas de requisições desnecessárias. Dois padrões resolvem isso.

Debounce espera o usuário "parar" de disparar o evento por um tempo, antes de executar a função:

Analogia É como um elevador esperto: ele não sai correndo assim que alguém aperta o botão — espera alguns segundos para ver se mais gente vai chegar e apertar também, e só então fecha a porta e sobe. Debounce é ótimo para caixas de busca: só busca depois que a pessoa parou de digitar. 
function debounce(funcao, atraso) {
  let temporizador;

  return function (...args) {
    clearTimeout(temporizador);
    temporizador = setTimeout(function () {
      funcao(...args);
    }, atraso);
  };
}

const buscarComDebounce = debounce(function (termo) {
  console.log("Buscando por:", termo);
}, 500);

campoDeBusca.addEventListener("input", function (e) {
  buscarComDebounce(e.target.value);
});
// Só dispara a busca 500ms depois da ÚLTIMA tecla digitada

Throttle é diferente: garante que a função execute no máximo uma vez a cada intervalo de tempo, não importa quantas vezes o evento dispare:

function throttle(funcao, intervalo) {
  let podeExecutar = true;

  return function (...args) {
    if (podeExecutar) {
      funcao(...args);
      podeExecutar = false;
      setTimeout(function () {
        podeExecutar = true;
      }, intervalo);
    }
  };
}

const aoRolar = throttle(function () {
  console.log("Posição da rolagem registrada");
}, 200);

window.addEventListener("scroll", aoRolar);
// Executa no máximo uma vez a cada 200ms, mesmo rolando sem parar
Dica Repare que tanto debounce quanto throttle são exemplos práticos de closures: a função retornada continua tendo acesso a temporizador ou podeExecutar muito depois de debounce()/throttle() terem terminado de executar. Os conceitos desta lição não são isolados — eles se combinam constantemente no código do dia a dia.

Juntando tudo

Closures dão às funções "memória" própria e privada. this determina de quem é o contexto de execução, e muda de acordo com a forma de chamada — exceto em arrow functions, que herdam o this de fora. Protótipos são o mecanismo por trás de como objetos compartilham comportamento, inclusive quando você usa class. E debounce/throttle mostram como esses fundamentos aparecem juntos, resolvendo problemas reais de performance em interfaces.

Resumo

  • Closure é quando uma função "carrega consigo" (como uma mochila) as variáveis do ambiente onde foi criada, mesmo depois desse ambiente ter terminado.
  • this depende de como a função é chamada, não de onde ela foi escrita.
  • Arrow functions não têm this próprio: elas herdam o this do escopo ao redor, o que evita bugs comuns em callbacks.
  • Protótipos são o mecanismo por trás de como objetos compartilham métodos, inclusive na sintaxe moderna de class.
  • Debounce espera o usuário parar de agir antes de executar; throttle limita a execução a um intervalo fixo, não importa a frequência do evento.
  • Debounce e throttle são aplicações práticas de closures — os conceitos avançados do JS se combinam o tempo todo em código real.
