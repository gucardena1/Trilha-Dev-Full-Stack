9. Testes

Testes unitários

Testando a menor peça possível do seu código, isolada de todo o resto.

Analogia Imagine uma fábrica de carros testando cada peça antes de montar o veículo inteiro: o parafuso é testado sozinho para ver se aguenta o peso previsto, o vidro é testado sozinho para ver se resiste a um impacto, o motor é testado sozinho numa bancada, sem estar preso a nenhum carro. Um teste unitário faz exatamente isso com o seu código: pega a menor peça possível — geralmente uma única função — e testa só ela, isolada de bancos de dados, redes, telas e de qualquer outra peça do sistema.

O que é uma "unidade"

Uma unidade é, na prática, a menor parte testável do seu código de forma isolada — quase sempre uma função, um método ou uma pequena classe. O critério que define se um teste é "unitário" não é o tamanho do código testado, mas sim o isolamento: um teste unitário não deve depender de banco de dados real, de chamadas de rede, do sistema de arquivos ou de qualquer outra parte externa ao pedaço de código que está sendo verificado. Se uma função soma dois números, o teste unitário chama essa função com valores conhecidos e confere se o resultado é o esperado — sem abrir conexão com nada.

Esse isolamento é o que torna os testes unitários tão rápidos: sem rede, sem disco, sem banco de dados, um teste unitário roda em milissegundos. Um projeto saudável pode ter milhares deles e ainda assim rodar a suíte inteira em poucos segundos — o que permite rodá-la a cada salvamento de arquivo, sem atrapalhar o fluxo de trabalho de quem está programando.

O padrão Arrange-Act-Assert

Quase todo teste unitário bem escrito segue a mesma estrutura em três partes, conhecida como AAA (Arrange, Act, Assert):

  • Arrange (organizar): prepara tudo que o teste vai precisar — cria os dados de entrada, instancia os objetos necessários, define os valores esperados.
  • Act (agir): executa a ação que está sendo testada — chama a função, com os dados preparados na etapa anterior.
  • Assert (afirmar): confere se o resultado obtido é de fato o resultado esperado. Se não for, o teste falha e avisa que algo está errado.

Essa estrutura existe para deixar qualquer teste fácil de ler, mesmo por quem não o escreveu: basta olhar as três partes, na ordem, para entender o que está sendo verificado e por quê.

Exemplo com PHPUnit (PHP)

Suponha uma função simples que calcula o preço final de um produto aplicando um desconto percentual. Primeiro, o código sendo testado: 

function calcularPrecoComDesconto(float $preco, float $percentualDesconto): float
{
    $desconto = $preco * ($percentualDesconto / 100);
    return $preco - $desconto;
}

Agora o teste unitário, usando o PHPUnit, a ferramenta de testes mais usada no mundo PHP:

use PHPUnit\Framework\TestCase;

class CalculadoraDePrecoTest extends TestCase
{
    public function testAplicaDezPorCentoDeDesconto(): void
    {
        // Arrange: preparamos os valores de entrada e o resultado esperado
        $precoOriginal = 200.0;
        $percentualDesconto = 10.0;
        $resultadoEsperado = 180.0;

        // Act: executamos a função que estamos testando
        $resultadoObtido = calcularPrecoComDesconto($precoOriginal, $percentualDesconto);

        // Assert: conferimos se o resultado bate com o esperado
        $this->assertEquals($resultadoEsperado, $resultadoObtido);
    }
}

Rodando phpunit no terminal, essa classe é executada automaticamente, e o PHPUnit informa se o teste passou (o resultado bateu) ou falhou (e, se falhou, mostra exatamente qual era o valor esperado e qual foi o valor obtido).

Exemplo com Vitest (JavaScript)

O mesmo raciocínio, agora em JavaScript, usando o Vitest — uma ferramenta de testes moderna e muito próxima do Jest, outra ferramenta popular no ecossistema JavaScript: 

// precos.js
export function calcularPrecoComDesconto(preco, percentualDesconto) {
  const desconto = preco * (percentualDesconto / 100);
  return preco - desconto;
}
// precos.test.js
import { describe, it, expect } from 'vitest';
import { calcularPrecoComDesconto } from './precos.js';

describe('calcularPrecoComDesconto', () => {
  it('aplica 10% de desconto corretamente', () => {
    // Arrange
    const precoOriginal = 200;
    const percentualDesconto = 10;
    const resultadoEsperado = 180;

    // Act
    const resultadoObtido = calcularPrecoComDesconto(precoOriginal, percentualDesconto);

    // Assert
    expect(resultadoObtido).toBe(resultadoEsperado);
  });
});

Repare que a estrutura é praticamente idêntica à do PHPUnit — só muda a sintaxe da linguagem. Isso não é coincidência: o padrão AAA é o mesmo em qualquer linguagem ou ferramenta de teste, porque descreve uma forma de pensar, não uma sintaxe específica.

Dica Dê nomes descritivos aos seus testes, como aplica_dez_por_cento_de_desconto em vez de teste1. Quando um teste falha meses depois, o nome sozinho já deveria contar boa parte da história do que quebrou, sem que ninguém precise abrir o código do teste para entender o que estava sendo verificado.

Mocks: fingindo as partes que você não quer testar de verdade

Nem todo código é tão isolado quanto uma calculadora de desconto. Muitas funções dependem de outras peças — um banco de dados, uma API externa, o relógio do sistema — que você não quer envolver de verdade num teste unitário, porque isso o tornaria lento, instável (a API pode estar fora do ar) ou até perigoso (imagine um teste que sem querer envia um e-mail de verdade para um cliente).

Um mock é uma versão falsa e controlada dessa dependência, criada só para o teste. Pense num mock como um ator dublê num filme de ação: ele não é o verdadeiro protagonista, mas se comporta exatamente como o roteiro pede naquela cena específica, permitindo gravar a cena sem o risco de usar a pessoa real. Se sua função envia um e-mail de confirmação, o teste unitário não precisa de um servidor de e-mail de verdade — ele usa um mock que apenas finge enviar, e o teste confere se a função tentou enviar o e-mail certo, para a pessoa certa. 

import { describe, it, expect, vi } from 'vitest';
import { notificarCliente } from './notificacoes.js';

describe('notificarCliente', () => {
  it('chama o serviço de e-mail com os dados corretos', () => {
    // Arrange: criamos um mock que substitui o envio de e-mail de verdade
    const servicoDeEmailFalso = { enviar: vi.fn() };

    // Act
    notificarCliente(servicoDeEmailFalso, 'ana@exemplo.com', 'Pedido confirmado');

    // Assert: conferimos que o mock foi chamado com os argumentos esperados,
    // sem que nenhum e-mail de verdade tenha saído
    expect(servicoDeEmailFalso.enviar).toHaveBeenCalledWith(
      'ana@exemplo.com',
      'Pedido confirmado'
    );
  });
});
Atenção Use mocks para isolar dependências externas (banco de dados, rede, tempo, arquivos) — não para fugir de testar o comportamento real da sua própria lógica. Um erro comum é "mockar demais" e acabar testando apenas se as funções foram chamadas, sem nunca verificar se o resultado final está correto. Prefira sempre testar o comportamento observável (o que a função retorna, o que ela realmente faz) em vez de detalhes de implementação (como exatamente ela faz por dentro) — testes presos a detalhes de implementação quebram toda vez que você refatora o código, mesmo sem introduzir nenhum bug.

Resumo

  • Uma unidade é a menor parte testável isoladamente — normalmente uma função ou método.
  • Todo teste unitário bem escrito segue o padrão Arrange-Act-Assert: organizar, agir, afirmar.
  • PHPUnit (PHP) e Vitest/Jest (JavaScript) são ferramentas populares para escrever e rodar testes unitários.
  • Mocks substituem dependências externas (banco, API, e-mail) por versões falsas e controladas.
  • Teste o comportamento observável da função, não os detalhes internos de como ela foi implementada.
