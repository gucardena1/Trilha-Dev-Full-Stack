1. Fundamentos & Lógica

Como pensar como programador

Você já conhece as ferramentas (variáveis, condicionais, loops, funções, listas). Agora vamos treinar o raciocínio que decide como usá-las.

Analogia Conhecer variáveis, ifs, loops e funções é como conhecer as ferramentas de uma caixa de ferramentas: martelo, chave de fenda, serra. Só que ter as ferramentas na mão não faz de ninguém um marceneiro — o que faz é saber qual ferramenta usar, em que ordem, e como quebrar um móvel grande (tipo um guarda-roupa) em partes menores e gerenciáveis (as prateleiras, as portas, as gavetas), que dá para construir uma de cada vez. Esta lição é sobre virar esse "marceneiro" do código: não vamos aprender nenhum comando novo, vamos aprender a pensar antes de escrever qualquer comando.

O maior erro de quem está aprendendo: tentar escrever código direto

É extremamente tentador, ao ler um problema, já abrir o editor e começar a digitar código imediatamente. Na prática, isso costuma sair pela culatra: você escreve um pedaço, percebe que não faz sentido, apaga, escreve de novo, trava, fica frustrado. O motivo é simples — você está tentando resolver duas coisas ao mesmo tempo: entender o problema e lembrar a sintaxe certa. Programadores experientes separam essas duas etapas. Primeiro entendem e planejam o problema em uma linguagem simples (às vezes até em português mesmo), só depois traduzem esse plano para código.

Técnica 1: decompor o problema em partes menores

Decompor significa pegar um problema grande e assustador e quebrá-lo em vários problemas pequenos e fáceis. Cada parte pequena, isoladamente, é simples o bastante para resolver com o que você já aprendeu nesta trilha (uma variável, um if, um loop, uma função). Vamos praticar com um exemplo real:

Problema: "Dada uma lista de compras (nome do produto e preço), calcular o valor total, aplicar 10% de desconto se o total passar de R$100, e mostrar uma mensagem final com o valor a pagar."

Um iniciante ansioso tentaria escrever tudo de uma vez. Um programador experiente quebra em pedaços:

  1. Somar os preços de todos os produtos da lista (isso, sozinho, é só um loop com um acumulador).
  2. Verificar se o total passa de R$100 (isso, sozinho, é só um if).
  3. Se passar, calcular o valor com 10% de desconto (isso, sozinho, é só uma conta).
  4. Montar e exibir a mensagem final (isso, sozinho, é só um console.log com template string).

Cada um desses quatro itens, isoladamente, é trivial — você já sabe fazer todos eles desde as lições anteriores. O "problema grande" só parecia difícil porque estava todo misturado numa frase só. Ao separar, cada parte vira uma função pequena, e a solução final é só a combinação delas: 

function calcularTotal(produtos) {
  let total = 0;
  for (const produto of produtos) {
    total = total + produto.preco;
  }
  return total;
}

function aplicarDesconto(total) {
  if (total > 100) {
    return total * 0.9; // 10% de desconto
  }
  return total; // sem desconto
}

function montarMensagem(valorFinal) {
  return `Valor a pagar: R$ ${valorFinal.toFixed(2)}`;
}

// Juntando as peças:
const produtos = [
  { nome: "Teclado", preco: 80 },
  { nome: "Mouse", preco: 40 },
];

const total = calcularTotal(produtos);
const valorFinal = aplicarDesconto(total);
const mensagem = montarMensagem(valorFinal);

console.log(mensagem); // Valor a pagar: R$ 108.00

Note como cada função tem uma única responsabilidade e um nome que descreve exatamente o que faz. Isso não é só estética: quando algo dá errado, você sabe exatamente onde procurar ("o total está errado? olha a calcularTotal. O desconto não aplicou? olha a aplicarDesconto"). Um bloco de código único e gigante, fazendo tudo misturado, é muito mais difícil de debugar.

Dica Uma boa pergunta para saber se você decompôs bem um problema: "eu consigo explicar o que esta função faz em uma frase curta, sem usar a palavra 'e'?" Se a resposta envolver "e" ("ela calcula o total e aplica desconto e formata a mensagem"), provavelmente essa função está fazendo coisa demais e deveria virar duas ou três funções menores.

Técnica 2: escrever pseudocódigo antes de codar

Pseudocódigo é escrever a lógica da solução em linguagem quase natural — português mesmo, ou uma mistura de português com estrutura de código — sem se preocupar com a sintaxe exata da linguagem de programação. O objetivo é validar se o raciocínio está certo antes de gastar energia lembrando onde vai cada chave, parênteses e ponto e vírgula.

Para o mesmo problema de calcular o total da compra, o pseudocódigo poderia ser: 

FUNÇÃO calcularTotal(lista de produtos):
    criar variável total, começando em 0
    PARA CADA produto na lista:
        somar o preço do produto ao total
    DEVOLVER total

FUNÇÃO aplicarDesconto(total):
    SE total for maior que 100:
        DEVOLVER total com 10% a menos
    SENÃO:
        DEVOLVER total sem alteração

INÍCIO:
    total = calcularTotal(produtos)
    valorFinal = aplicarDesconto(total)
    MOSTRAR mensagem com valorFinal

Repare que esse pseudocódigo já tem a mesma estrutura lógica da solução final em JavaScript — só que sem nenhuma das exigências rígidas de sintaxe (aspas, ponto e vírgula, chaves). Isso é proposital: o pseudocódigo serve para você (ou seu time) validar a ideia. Depois que a ideia está clara e correta, traduzir para JavaScript, Python ou qualquer outra linguagem vira um trabalho quase mecânico.

Atenção Pseudocódigo não tem regra fixa nem "sintaxe oficial" — o objetivo dele é comunicar uma ideia com clareza, não seguir um padrão rígido. Não se preocupe em fazer "certo"; preocupe-se em fazer claro, de um jeito que você (ou outra pessoa) consiga ler e entender o plano sem executar nada.

Técnica 3: o pato de borracha (rubber duck debugging)

Essa é uma das técnicas mais famosas — e mais estranhas à primeira vista — da programação. A ideia surgiu de um costume real de alguns desenvolvedores: manter um pato de borracha (o brinquedo de banheira mesmo) na mesa, e, quando o código não funciona e a causa não é óbvia, explicar o problema em voz alta para o pato, linha por linha, como se ele fosse uma pessoa que não sabe nada sobre o código.

O motivo disso funcionar não tem nada de mágico: o processo de verbalizar um raciocínio — transformar pensamento vago em frases completas e ordenadas — obriga seu cérebro a examinar cada passo com mais cuidado do que quando você só "olha" o código por cima. Muitas vezes, no meio da explicação, a pessoa percebe sozinha onde está o erro, antes mesmo de terminar a frase ("...e aqui eu comparo o índice com o tamanho da lista, então... ah, espera, aqui devia ser < e não <=!").

Você não precisa literalmente ter um pato de borracha (embora seja divertido ter um). A técnica funciona igualmente bem explicando para um colega, para uma planta no vaso, ou até escrevendo a explicação num papel. O ingrediente essencial não é o ouvinte — é o ato de colocar seu raciocínio em palavras completas e sequenciais, em vez de deixá-lo solto e impreciso na sua cabeça.

Dica Quando for "explicar para o pato", seja bem literal: "esta variável guarda isso. Esta linha faz aquilo. Depois disso, eu espero que o valor seja X." Resista à tentação de pular etapas "óbvias" — geralmente é exatamente numa etapa "óbvia demais para checar" que o erro está escondido.

Juntando as três técnicas num fluxo de trabalho

Na prática, um fluxo saudável para resolver qualquer problema de programação, do mais simples ao mais complexo, segue mais ou menos esta ordem:

  1. Entenda o problema antes de tudo. Se não conseguir explicar o problema em uma frase clara, ainda não está pronto para codar.
  2. Decomponha o problema grande em partes pequenas e independentes.
  3. Escreva o pseudocódigo de cada parte pequena, validando o raciocínio sem se preocupar com sintaxe.
  4. Traduza o pseudocódigo para código real, uma parte de cada vez, testando cada parte antes de seguir para a próxima.
  5. Quando travar num bug que não faz sentido, explique em voz alta, linha por linha, para o pato (ou para quem estiver por perto).

Note que esse fluxo é o mesmo, seja o problema "calcular o total de uma compra" (o exemplo desta lição) ou "construir um sistema de login" (um problema bem mais complexo, que você vai encontrar mais adiante na trilha). A escala muda, mas o raciocínio — decompor, planejar antes de codar, verbalizar quando travar — é exatamente o mesmo. É essa forma de pensar, mais do que a sintaxe de qualquer linguagem específica, que realmente define alguém como programador.

Resumo

  • Separe "entender o problema" de "escrever a sintaxe certa" — tentar fazer os dois ao mesmo tempo costuma travar o raciocínio.
  • Decomponha problemas grandes em partes pequenas, cada uma resolvível com uma função simples e uma única responsabilidade.
  • Escreva pseudocódigo (em português, sem regras fixas) para validar a lógica antes de traduzir para uma linguagem real.
  • Use a técnica do pato de borracha: explicar o problema em voz alta, linha por linha, ajuda a encontrar erros escondidos.
  • Esse fluxo — entender, decompor, planejar, codar, verbalizar quando travar — funciona em qualquer escala de problema, do mais simples ao mais complexo.
