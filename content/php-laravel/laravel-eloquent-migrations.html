6. PHP & Laravel

Eloquent e migrations

Como o Laravel conversa com o banco de dados sem que você precise escrever SQL na mão o tempo todo.

Analogia Migrations são como o histórico de alterações de uma planta de construção civil. Em vez de reformar uma casa e ninguém anotar o que mudou, cada reforma vira uma "ficha datada": "dia 1, construímos a garagem", "dia 15, adicionamos um banheiro", "dia 30, aumentamos a cozinha". Qualquer pessoa da equipe, em qualquer computador, consegue reconstruir a casa do zero seguindo essas fichas em ordem — e todo mundo sabe exatamente o estado atual da estrutura. Migrations fazem isso com a estrutura do banco de dados: cada arquivo de migration é uma "ficha" datada que descreve uma mudança nas tabelas, e o histórico completo é versionado junto com o código, igual você já faz com Git.

O que é um ORM e por que ele existe

Sem um framework, para buscar dados num banco você escreveria SQL diretamente, por exemplo SELECT * FROM produtos WHERE preco > 100, e depois trataria manualmente o resultado bruto devolvido pelo banco. Isso funciona, mas é repetitivo, propenso a erros de digitação, e abre brechas de segurança se você concatenar valores de usuário direto na query (o famoso ataque de SQL Injection).

Um ORM (Object-Relational Mapper, "mapeador objeto-relacional") é uma camada que traduz entre tabelas do banco de dados e classes/objetos do PHP. Em vez de escrever SQL na mão, você trabalha com objetos comuns da linguagem, e o ORM gera o SQL necessário por trás das cenas, já protegido contra os ataques mais comuns. O ORM do Laravel se chama Eloquent. 

// Sem ORM (SQL puro, mais verboso e mais arriscado)
$pdo = new PDO(...);
$stmt = $pdo->prepare("SELECT * FROM produtos WHERE preco > ?");
$stmt->execute([100]);
$produtos = $stmt->fetchAll();

// Com Eloquent (muito mais direto)
$produtos = Produto::where('preco', '>', 100)->get();

Migrations: controle de versão do banco de dados

Diferente de um arquivo de código, uma tabela de banco de dados não pode simplesmente ser "commitada" no Git — ela é uma estrutura que existe dentro do próprio banco. As migrations resolvem esse problema: são arquivos PHP que descrevem, passo a passo, como criar ou alterar tabelas. Elas ficam versionadas junto com o resto do código, então qualquer desenvolvedor que clonar o projeto consegue recriar a estrutura exata do banco rodando um único comando. 

php artisan make:migration create_produtos_table

Isso gera um arquivo em database/migrations com um nome como 2026_07_24_000000_create_produtos_table.php, contendo dois métodos: up() (o que fazer para aplicar a mudança) e down() (como desfazer, caso precise reverter). 

<?php

use Illuminate\Database\Migrations\Migration;
use Illuminate\Database\Schema\Blueprint;
use Illuminate\Support\Facades\Schema;

return new class extends Migration
{
    public function up(): void
    {
        Schema::create('produtos', function (Blueprint $table) {
            $table->id();
            $table->string('nome');
            $table->decimal('preco', 8, 2);
            $table->timestamps(); // cria created_at e updated_at automaticamente
        });
    }

    public function down(): void
    {
        Schema::dropIfExists('produtos');
    }
};

Depois de criar (ou receber de um colega) uma migration, você aplica a mudança de fato no banco com: 

php artisan migrate

Esse comando roda todas as migrations ainda não aplicadas, na ordem correta (baseada na data no nome do arquivo). Assim, um mesmo projeto pode ter sua estrutura de banco reproduzida de forma idêntica na máquina de qualquer desenvolvedor da equipe, ou no servidor de produção.

Atenção Um erro extremamente comum de quem está aprendendo Laravel é criar a migration mas esquecer de rodar php artisan migrate — e então ficar confuso porque o Eloquent reclama que a tabela "não existe". Criar o arquivo de migration só descreve a mudança; ela só é aplicada de verdade no banco depois do migrate.

Criando um Model Eloquent

Um Model é uma classe PHP que representa uma tabela do banco. Por padrão, o Eloquent assume que o Model Produto corresponde à tabela produtos (nome no plural, em minúsculas) — uma convenção que evita configuração repetitiva. 

php artisan make:model Produto
<?php

namespace App\Models;

use Illuminate\Database\Eloquent\Model;

class Produto extends Model
{
    protected $fillable = ['nome', 'preco'];
}

Com o Model criado, você já consegue fazer operações no banco sem escrever SQL: 

// Criar um novo registro
Produto::create(['nome' => 'Teclado', 'preco' => 150]);

// Buscar todos os produtos
$produtos = Produto::all();

// Buscar um produto específico pelo id
$produto = Produto::find(1);

// Filtrar com condições
$caros = Produto::where('preco', '>', 500)->get();

// Atualizar
$produto = Produto::find(1);
$produto->preco = 200;
$produto->save();

// Excluir
Produto::destroy(1);
Dica A propriedade $fillable lista quais campos podem ser preenchidos em massa (como no Produto::create([...])). Isso é uma proteção de segurança chamada mass assignment protection: sem declarar $fillable, o Laravel bloqueia a criação em massa por padrão, evitando que um usuário mal-intencionado envie campos extras (como is_admin => true) que você não pretendia deixar preencher diretamente por um formulário.

Relacionamentos: hasMany e belongsTo

Bancos de dados relacionais existem justamente para relacionar tabelas entre si. Imagine que cada Categoria pode ter vários Produtos, e cada produto pertence a uma única categoria. O Eloquent representa essa relação diretamente nos Models, como métodos: 

<?php
// app/Models/Categoria.php
class Categoria extends Model
{
    // Uma categoria TEM VÁRIOS produtos
    public function produtos()
    {
        return $this->hasMany(Produto::class);
    }
}

// app/Models/Produto.php
class Produto extends Model
{
    protected $fillable = ['nome', 'preco', 'categoria_id'];

    // Um produto PERTENCE A uma categoria
    public function categoria()
    {
        return $this->belongsTo(Categoria::class);
    }
}

Para essa relação funcionar, a tabela produtos precisa ter uma coluna categoria_id (definida na migration com $table->foreignId('categoria_id')->constrained()), que guarda a qual categoria cada produto pertence. Com os relacionamentos definidos, navegar entre os dados fica natural: 

$categoria = Categoria::find(1);
foreach ($categoria->produtos as $produto) {
    echo $produto->nome;
}

$produto = Produto::find(5);
echo $produto->categoria->nome; // acessa a categoria "dona" desse produto

Repare que hasMany e belongsTo são "dois lados da mesma moeda": quem tem hasMany é o lado "um" da relação (uma categoria, vários produtos); quem tem belongsTo é o lado "muitos" (cada produto pertence a uma categoria só). Essa dupla é a base de praticamente todo relacionamento simples entre tabelas no Eloquent.

Resumo

  • Um ORM traduz entre tabelas do banco e classes PHP, evitando escrever SQL manualmente na maioria dos casos.
  • Migrations são arquivos versionados que descrevem mudanças na estrutura do banco, aplicadas com php artisan migrate.
  • Esquecer de rodar migrate depois de criar uma migration é um erro comum e gera erro de "tabela não existe".
  • Um Model Eloquent representa uma tabela; por convenção, Produto corresponde à tabela produtos.
  • $fillable protege contra mass assignment, definindo quais campos podem ser preenchidos em massa.
  • hasMany e belongsTo definem os dois lados de um relacionamento um-para-muitos entre Models.
