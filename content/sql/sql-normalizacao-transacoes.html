5. SQL & Bancos de Dados

Normalização e transações

Como desenhar tabelas que não se contradizem, e como garantir que operações compostas nunca fiquem "pela metade".

Analogia Normalizar um banco de dados é como arrumar um guarda-roupa bagunçado: em vez de jogar tudo misturado numa gaveta só (meias com camisas com o carregador de celular), você separa cada tipo de coisa no lugar certo, de forma que exista um único lugar correto para cada item. Se amanhã você quiser saber quantas meias tem, não precisa vasculhar o guarda-roupa inteiro — você já sabe exatamente onde procurar, e não existe risco de ter "meias" espalhadas (e contadas de forma diferente) em três gavetas ao mesmo tempo.

O problema que a normalização resolve

Imagine esta tabela única, guardando pedidos e dados do cliente juntos:

idcliente_nomecliente_emailprodutovalor
1Ana Souzaana@email.comTeclado150.00
2Ana Souzaana@emial.comMouse60.00
3Bruno Limabruno@email.comMonitor900.00

Repare no e-mail da linha 2: está escrito ana@emial.com, com um erro de digitação, diferente do e-mail correto na linha 1. Nada nessa estrutura impede essa inconsistência — o mesmo cliente aparece com dois e-mails "diferentes" dependendo de qual pedido você olhar. Esse tipo de problema é o motivo pelo qual existe a normalização: um conjunto de boas práticas para organizar tabelas de forma que cada informação tenha um único lugar de verdade, evitando repetição e contradição.

As formas normais, na prática

Formalmente existem várias "formas normais" (1FN, 2FN, 3FN...), com definições bem técnicas. Para o uso do dia a dia, vale entender a ideia prática por trás das três primeiras, que já resolvem a grande maioria dos problemas reais:

  • 1ª Forma Normal (1FN): cada célula guarda um valor só. Uma coluna telefones com o valor "11999999999, 11888888888" dentro de uma única célula viola a 1FN — ali deveriam existir linhas separadas (numa tabela telefones à parte) ou, no mínimo, uma estrutura própria para múltiplos valores.
  • 2ª Forma Normal (2FN): toda coluna depende da chave inteira, não só de parte dela. Na tabela de pedidos acima, cliente_nome e cliente_email não dependem do pedido em si — dependem do cliente. Isso é sinal de que essas colunas deveriam morar numa tabela clientes separada, ligada por chave estrangeira (exatamente como fizemos nas lições anteriores).
  • 3ª Forma Normal (3FN): nenhuma coluna depende de outra coluna que não seja a chave. Por exemplo, se uma tabela de pedidos tivesse cep e também cidade, e a cidade pudesse ser deduzida a partir do CEP, isso é uma dependência "escondida" que deveria ser separada.

Aplicando a normalização ao exemplo anterior, chegamos de volta ao modelo que já usamos nas lições passadas:

clientes
idnomeemail
1Ana Souzaana@email.com
2Bruno Limabruno@email.com
pedidos
idprodutocliente_id
1Teclado1
2Mouse1
3Monitor2

Agora o e-mail de Ana Souza existe em um único lugar. Se ele estiver errado, você corrige uma vez só, e todos os pedidos dela automaticamente "enxergam" o e-mail corrigido através da chave estrangeira cliente_id.

Dica Normalização não é um dogma absoluto. Em sistemas com necessidade extrema de velocidade de leitura, às vezes se opta deliberadamente por "desnormalizar" (repetir alguns dados) para evitar JOINs custosos. Mas isso é uma decisão consciente feita depois de entender bem o modelo normalizado — não um atalho para quem está começando.

Transações: operações que precisam acontecer "tudo ou nada"

Agora um problema diferente: imagine uma transferência bancária entre duas contas. Isso exige dois passos no banco de dados — tirar dinheiro da conta A e colocar na conta B: 

UPDATE contas SET saldo = saldo - 100 WHERE id = 1;
UPDATE contas SET saldo = saldo + 100 WHERE id = 2;

E se, entre esses dois comandos, o servidor cair, a internet falhar ou o programa travar? Existe o risco real de o dinheiro sair da conta 1 e nunca chegar na conta 2 — ele simplesmente desaparece. Para evitar exatamente esse tipo de desastre, os bancos de dados oferecem transações: um jeito de agrupar vários comandos SQL para que eles sejam tratados como uma única operação indivisível. Ou tudo é aplicado com sucesso, ou nada é aplicado — nunca fica "pela metade". 

BEGIN;

UPDATE contas SET saldo = saldo - 100 WHERE id = 1;
UPDATE contas SET saldo = saldo + 100 WHERE id = 2;

COMMIT;

BEGIN abre a transação, avisando ao banco "os próximos comandos fazem parte de um mesmo pacote". COMMIT confirma tudo de uma vez, tornando as mudanças permanentes. Se algo der errado no meio do caminho, a aplicação pode chamar ROLLBACK em vez de COMMIT, desfazendo tudo o que foi feito desde o BEGIN — como se nada tivesse acontecido. 

BEGIN;

UPDATE contas SET saldo = saldo - 100 WHERE id = 1;
-- algo deu errado aqui (ex: conta 2 não existe)
ROLLBACK;
-- a subtração acima é desfeita, como se nunca tivesse rodado

ACID: as quatro garantias por trás de uma transação

As transações confiáveis se apoiam em quatro garantias conhecidas pela sigla ACID. Explicando cada uma de forma simples, sem jargão:

  • Atomicidade (Atomicity). Todos os comandos da transação são tratados como uma coisa só — "tudo ou nada", exatamente como no exemplo da transferência bancária.
  • Consistência (Consistency). A transação sempre leva o banco de um estado válido para outro estado válido, respeitando todas as regras definidas (chaves únicas, chaves estrangeiras corretas etc.). Nunca fica um estado "quebrado" no meio do caminho.
  • Isolamento (Isolation). Mesmo que várias transações aconteçam ao mesmo tempo (centenas de pessoas usando o banco simultaneamente), cada transação enxerga o banco como se fosse a única rodando naquele momento — uma não "vê" os passos intermediários incompletos da outra.
  • Durabilidade (Durability). Depois que um COMMIT é confirmado, a mudança é permanente — mesmo que o servidor caia um segundo depois, os dados já gravados não somem.
Atenção Fora de uma transação explícita, a maioria dos bancos trata cada comando SQL isolado como sua própria "mini transação" automática. Mas isso não ajuda quando a regra de negócio exige que vários comandos aconteçam juntos, como no exemplo da transferência. Sempre que uma operação envolver mais de um INSERT/UPDATE/DELETE que precisam ser consistentes entre si, vale embrulhar tudo entre BEGIN e COMMIT.

Resumo

  • Normalização organiza tabelas para que cada dado tenha um único lugar de verdade, evitando repetição e contradição.
  • 1FN: uma célula, um valor. 2FN: colunas dependem da chave inteira. 3FN: nenhuma coluna depende de outra coluna que não seja a chave.
  • Uma transação (BEGIN ... COMMIT/ROLLBACK) agrupa vários comandos SQL como uma operação única, "tudo ou nada".
  • ACID resume as quatro garantias de uma transação confiável: Atomicidade, Consistência, Isolamento e Durabilidade.
  • Operações que envolvem mais de um comando dependente entre si (como transferências) devem sempre estar dentro de uma transação.
