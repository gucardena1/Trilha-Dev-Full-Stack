5. SQL & Bancos de Dados

Índices e performance

Por que a mesma consulta pode levar 3 milissegundos numa tabela e 30 segundos em outra — e o que fazer sobre isso.

Analogia Pense num livro grosso de 800 páginas sem nenhum índice remissivo no final. Se alguém pedir "encontre todas as páginas que falam sobre 'transações'", você só tem um jeito: folhear o livro inteiro, página por página, do início ao fim. Agora imagine que o livro tem, no final, um índice remissivo: "transações: páginas 45, 312, 501". Com o índice, você vai direto às páginas certas, sem folhear nada. Um índice de banco de dados é exatamente isso: uma estrutura auxiliar que guarda, de forma ordenada, "para este valor de uma coluna, a linha está em tal lugar", permitindo pular direto para o dado certo em vez de examinar a tabela inteira.

O que acontece sem índice: table scan

Sem um índice na coluna que você está filtrando, o banco de dados faz o que se chama de table scan (ou full scan): ele lê linha por linha, do começo ao fim da tabela, conferindo se cada uma bate com a condição do WHERE. Numa tabela de 200 linhas, isso é instantâneo — o computador nem sente. Numa tabela de 50 milhões de linhas, isso pode levar segundos ou minutos, porque o trabalho cresce proporcionalmente ao tamanho da tabela. 

SELECT * FROM pedidos
WHERE cliente_id = 4821;

Se cliente_id não tiver um índice e a tabela pedidos tiver milhões de linhas, esse SELECT aparentemente simples pode ficar lento — o banco precisa examinar cada pedido existente para descobrir quais pertencem ao cliente 4821.

Criando um índice

A sintaxe para criar um índice é direta: você escolhe um nome para o índice, a tabela e a coluna (ou colunas) que ele vai acelerar. 

CREATE INDEX idx_pedidos_cliente_id
ON pedidos (cliente_id);

A partir daí, o banco de dados mantém uma estrutura ordenada (geralmente uma árvore, chamada B-tree) apontando cada valor de cliente_id para as linhas correspondentes — como o índice remissivo do livro. A consulta anterior, que antes exigia examinar a tabela inteira, passa a "pular" direto para as linhas do cliente 4821.

Quando vale a pena criar um índice

Índice não é "sempre bom, crie em tudo" — ele tem um custo. Cada índice ocupa espaço em disco e precisa ser atualizado toda vez que uma linha é inserida, alterada ou apagada, o que deixa essas operações de escrita um pouco mais lentas. Por isso, a regra prática é: crie índices nas colunas que você consulta com frequência em cláusulas WHERE, JOIN ou ORDER BY — tipicamente:

  • Chaves primárias (a maioria dos bancos já cria esse índice automaticamente).
  • Chaves estrangeiras usadas em JOIN, como cliente_id no exemplo acima.
  • Colunas usadas com frequência em filtros, como email numa tabela de usuários (para buscas de login) ou status num sistema de pedidos.

Por outro lado, não faz sentido criar índice numa coluna que quase nunca aparece num WHERE, ou numa tabela pequena (poucas centenas de linhas), onde o table scan já é rápido o suficiente e o índice só adicionaria custo sem benefício perceptível.

Dica Uma metáfora útil: adicionar índice em toda coluna é como colocar um índice remissivo para cada palavra do livro, incluindo "o", "de" e "para". Tecnicamente funciona, mas o livro (o banco) fica pesado e mais lento para escrever, sem ganho real de utilidade na maioria das buscas.

EXPLAIN: pedindo para o banco mostrar o plano

Como saber se uma consulta está usando um índice ou fazendo um table scan? A maioria dos bancos relacionais oferece o comando EXPLAIN, que mostra o plano de execução — os passos internos que o banco vai seguir para resolver a consulta, sem executá-la de verdade. 

EXPLAIN SELECT * FROM pedidos
WHERE cliente_id = 4821;

O resultado (o formato varia entre PostgreSQL, MySQL etc.) costuma indicar se a consulta vai usar um "Index Scan" (bom sinal, está usando o índice) ou um "Seq Scan" / "Full Table Scan" (a tabela inteira será percorrida). Você não precisa decorar todos os detalhes do EXPLAIN agora — o importante é saber que ele existe e que é a ferramenta certa para investigar "por que essa consulta está lenta?".

Uma armadilha comum: o problema N+1

Existe um problema de performance muito comum que não tem relação com faltar índice, e sim com a forma como o código da aplicação consulta o banco: o chamado problema N+1. Em uma frase: ele acontece quando o código busca uma lista de N registros com uma consulta, e depois, para cada um dos N registros, dispara mais uma consulta separada ao banco — resultando em 1 + N consultas onde uma única consulta com JOIN resolveria tudo de uma vez. Por exemplo, buscar 100 clientes e depois, em um laço de repetição, buscar os pedidos de cada cliente um por um gera 101 idas ao banco em vez de uma só. Esse é um tema mais avançado que você vai encontrar de novo ao estudar ORMs (ferramentas que geram SQL automaticamente a partir de código), mas já vale guardar o nome — reconhecer "isso parece um N+1" é meio caminho andado para resolver problemas de lentidão no futuro.

Atenção Um índice acelera SELECT, mas não é mágica: ele não ajuda se a consulta usa uma função sobre a coluna indexada (como WHERE LOWER(email) = ...) sem um índice preparado para isso, nem se o WHERE filtra por uma coluna diferente da indexada. Sempre confira com EXPLAIN antes de assumir que "colocar um índice" resolveu o problema.

Resumo

  • Sem índice, o banco faz um table scan: examina a tabela inteira, linha por linha, para achar o que o WHERE pede.
  • Um índice é como o índice remissivo de um livro: permite pular direto para os dados certos, sem varrer tudo.
  • CREATE INDEX nome ON tabela (coluna); cria um índice; use em colunas muito consultadas em WHERE/JOIN/ORDER BY.
  • Índices custam espaço e deixam escritas (INSERT/UPDATE/DELETE) um pouco mais lentas — não crie em tudo.
  • EXPLAIN mostra o plano de execução de uma consulta, revelando se ela está usando um índice ou fazendo table scan.
  • O problema N+1 é disparar uma consulta extra para cada item de uma lista, em vez de resolver tudo com um único JOIN.
