10. Arquitetura & Performance

Camadas e API REST

Como organizar um backend em fatias de responsabilidade, e como expor essas fatias para o mundo através de uma API que qualquer cliente HTTP consegue conversar.

Analogia Pense num restaurante. O garçom (controller) recebe o pedido do cliente, traduz para a cozinha e devolve o prato pronto — ele não sabe cozinhar, só sabe conversar com o cliente e repassar o pedido. A cozinha (service) é onde a receita de verdade acontece: as regras do prato, o tempero, o ponto da carne — a lógica do negócio. E o estoque (repository) é quem sabe exatamente onde cada ingrediente está guardado e como buscá-lo, sem que a cozinha precise se preocupar se a cebola está na prateleira 3 ou 4. Cada um faz sua parte e não invade o trabalho do outro: se o restaurante trocar de fornecedor de ingredientes, a cozinha nem percebe; se mudar a receita, o garçom continua entregando o prato do mesmo jeito.

Arquitetura em camadas: controller, service, repository

Uma das formas mais comuns de organizar um backend é dividir o código em camadas, cada uma com uma responsabilidade clara e comunicação apenas com a camada vizinha:

  • Controller (ou "route handler"): recebe a requisição HTTP, extrai os dados (parâmetros, corpo, cabeçalhos), chama o service certo e devolve a resposta HTTP formatada. Não deveria conter regra de negócio.
  • Service: contém as regras de negócio de verdade — validações, cálculos, decisões. É a camada que "sabe" o que o sistema faz, sem saber nada sobre HTTP nem sobre SQL.
  • Repository: conversa com a fonte de dados (banco de dados, cache, API externa). Sabe como buscar e salvar, mas não sabe por quê — isso é papel do service.
// repository — só sabe conversar com o banco
class PedidoRepository {
  async buscarPorId(id) {
    return db.query("SELECT * FROM pedidos WHERE id = ?", [id]);
  }
  async salvar(pedido) {
    return db.query("INSERT INTO pedidos (...) VALUES (...)", [pedido]);
  }
}

// service — só sabe a regra de negócio, não sabe nada de HTTP nem de SQL
class PedidoService {
  constructor(pedidoRepository) {
    this.pedidoRepository = pedidoRepository;
  }
  async criarPedido(dadosPedido) {
    if (!dadosPedido.itens || dadosPedido.itens.length === 0) {
      throw new Error("Pedido precisa de ao menos um item");
    }
    const total = dadosPedido.itens.reduce((s, i) => s + i.preco * i.quantidade, 0);
    const pedido = { ...dadosPedido, total, status: "pendente" };
    return this.pedidoRepository.salvar(pedido);
  }
}

// controller — só sabe conversar com HTTP, delega a lógica pro service
class PedidoController {
  constructor(pedidoService) {
    this.pedidoService = pedidoService;
  }
  async criar(req, res) {
    try {
      const pedido = await this.pedidoService.criarPedido(req.body);
      res.status(201).json(pedido);
    } catch (erro) {
      res.status(400).json({ mensagem: erro.message });
    }
  }
}

O benefício mais prático dessa separação: você consegue testar PedidoService sem subir um servidor HTTP e sem um banco de dados real (basta passar um PedidoRepository falso, "de mentira", nos testes). E se um dia o sistema ganhar uma segunda porta de entrada — por exemplo, um comando de linha ou uma fila de mensagens, além da API HTTP — o PedidoService pode ser reaproveitado integralmente, porque ele nunca dependeu de req e res.

Dica Uma forma rápida de auditar se as camadas estão corretas: procure por SELECT/INSERT fora do repository, ou por req.body/res.json fora do controller. Se aparecerem fora do lugar esperado, é sinal de que uma camada está "vazando" para dentro da outra.

O que é uma API REST

API (Application Programming Interface) é qualquer forma padronizada de um sistema conversar com outro. Uma API REST (Representational State Transfer) é um estilo específico de API que usa o protocolo HTTP — o mesmo que o navegador usa para carregar páginas — para representar operações sobre recursos. Um recurso é qualquer "coisa" que o sistema expõe: um usuário, um pedido, um produto. Cada recurso tem uma URL própria, e as ações sobre ele são expressas pelo verbo HTTP usado na requisição, não pelo texto da URL.

VerboAçãoExemplo de URL
GETBuscar/ler um recurso (não deve alterar nada)GET /pedidos/42
POSTCriar um novo recursoPOST /pedidos
PUTSubstituir um recurso inteiro por um novoPUT /pedidos/42
PATCHAtualizar parcialmente um recursoPATCH /pedidos/42
DELETERemover um recursoDELETE /pedidos/42
Atenção Um erro comum de quem está aprendendo REST é criar URLs com verbos dentro, como GET /buscarPedido?id=42 ou POST /criarNovoPedido. Em REST, a URL identifica o recurso (/pedidos/42), e o verbo HTTP já diz a ação. Repetir a ação na URL é redundante e foge da convenção que faz o REST ser previsível entre sistemas diferentes.

Status codes: a resposta que a URL sozinha não dá

Todo retorno HTTP vem acompanhado de um código de status — um número de três dígitos que resume o resultado da operação antes mesmo de o cliente ler o corpo da resposta. Eles são agrupados por faixa:

CódigoSignificadoQuando usar
200 OKSucesso genéricoGET, PUT ou PATCH que deram certo
201 CreatedRecurso criado com sucessoPOST que criou algo novo
204 No ContentSucesso, sem corpo de respostaDELETE que deu certo
400 Bad RequestO cliente enviou dados inválidosCorpo mal formado, campo obrigatório faltando
401 UnauthorizedFalta autenticação (quem é você?)Token ausente ou inválido
403 ForbiddenEstá autenticado, mas não tem permissãoUsuário logado tentando acessar recurso de outro
404 Not FoundO recurso não existeGET /pedidos/999 quando o pedido 999 não existe
409 ConflictConflito com o estado atualTentar criar um e-mail que já está cadastrado
500 Internal Server ErrorErro inesperado no servidorExceção não tratada, bug

Usar o código certo importa porque clientes HTTP (navegadores, bibliotecas como fetch, outros sistemas) tomam decisões automáticas baseadas nele — por exemplo, tratar qualquer 4xx/5xx como erro sem precisar interpretar o texto da mensagem.

O que torna uma API verdadeiramente "RESTful"

Nem toda API que devolve JSON é "RESTful" de fato. Algumas características que definem o estilo REST:

  • Stateless (sem estado): cada requisição contém tudo que o servidor precisa para processá-la (inclusive autenticação, geralmente via token). O servidor não guarda "sessão" de conversa entre uma requisição e outra.
  • Recursos identificados por URL: cada "coisa" do sistema tem seu endereço próprio (/usuarios/7, /usuarios/7/pedidos), não parâmetros escondidos numa única URL genérica.
  • Verbos HTTP com significado consistente: GET nunca deveria alterar dados; DELETE sempre remove; a mesma ação sempre usa o mesmo verbo em toda a API.
  • Representações padronizadas: o mesmo recurso é sempre representado no mesmo formato (normalmente JSON), com nomes de campos consistentes entre endpoints.

Na prática, poucas APIs seguem a definição acadêmica de REST à risca (como a exigência de "HATEOAS", onde cada resposta traz links para as próximas ações possíveis) — o que o mercado chama de "API REST" no dia a dia é, na maioria das vezes, uma API HTTP organizada por recursos e verbos, o que já cobre os principais ganhos práticos: previsibilidade, cacheabilidade e um vocabulário comum entre times diferentes.

Resumo

  • Controller lida com HTTP, service com regra de negócio, repository com acesso a dados — cada um só conversa com o vizinho.
  • Separar em camadas facilita testes isolados e permite reaproveitar regras de negócio fora do contexto HTTP.
  • Em REST, a URL identifica o recurso e o verbo HTTP (GET, POST, PUT, PATCH, DELETE) expressa a ação.
  • Status codes comunicam o resultado da operação de forma padronizada, permitindo tratamento automático por clientes.
  • Uma API RESTful é stateless, organizada por recursos com URLs próprias, e usa os verbos de forma consistente.
