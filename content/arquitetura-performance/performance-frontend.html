10. Arquitetura & Performance

Performance no frontend

Um site rápido não é luxo: é a diferença entre um visitante que fica e um que fecha a aba antes mesmo de ver o conteúdo.

Analogia Imagine chegar a um restaurante e o garçom trazer, de uma vez só, os vinte pratos do cardápio inteiro pra mesa — mesmo que você só vá comer três. Você espera muito mais tempo até a primeira garfada, a mesa fica lotada de coisa que você nem pediu, e boa parte da comida esfria sem ser tocada. Um site lento costuma cometer o mesmo erro: carrega tudo de uma vez (imagens gigantes, todo o JavaScript do site inteiro, fontes que ninguém vai ler) antes de deixar o visitante ver qualquer coisa útil. Performance de frontend é, na essência, servir primeiro o que a pessoa precisa agora, e deixar o resto para depois — ou só quando for realmente pedido.

Performance de frontend importa por um motivo muito concreto: estudos de mercado mostram, repetidamente, que cada segundo extra de carregamento reduz a taxa de conversão e aumenta a taxa de abandono — em e-commerce, isso se traduz diretamente em dinheiro perdido. Além do fator comercial, mecanismos de busca (como o Google) usam sinais de performance como parte do ranqueamento de páginas, então um site lento também aparece pior nos resultados de busca.

Lazy loading: carregar só quando for preciso

Lazy loading ("carregamento preguiçoso") é a técnica de adiar o carregamento de um recurso até o momento em que ele realmente vai ser exibido ou usado. O exemplo mais comum é imagens: numa página longa, com 50 imagens, não faz sentido baixar as 45 que estão lá embaixo antes mesmo do visitante rolar a página até elas. 

<!-- Sem lazy loading: o navegador baixa a imagem assim que a página carrega,
     mesmo que ela esteja no rodapé, bem longe do que a pessoa está vendo -->
<img src="banner-grande.jpg" alt="Banner promocional" />

<!-- Com lazy loading nativo do navegador: a imagem só é baixada
     quando está prestes a entrar na área visível da tela -->
<img src="banner-grande.jpg" alt="Banner promocional" loading="lazy" />

O mesmo princípio se aplica a componentes JavaScript inteiros. Em aplicações modernas (React, Vue, e similares), é comum dividir o código em pedaços ("code splitting") e só baixar o código de uma tela quando o usuário realmente navega até ela — por exemplo, o código do painel administrativo não precisa ser baixado por um visitante que só está olhando a página inicial. 

// Sem lazy loading: o componente pesado é importado sempre, mesmo se o usuário nunca abrir esse modal
import RelatorioComGraficos from "./RelatorioComGraficos";

// Com lazy loading: o código só é baixado quando o componente realmente for usado
const RelatorioComGraficos = lazy(() => import("./RelatorioComGraficos"));

Otimização de imagens

Imagens costumam ser o maior peso de uma página em kilobytes transferidos. Algumas práticas reduzem drasticamente esse peso sem sacrificar a qualidade visual percebida:

  • Formato certo: formatos modernos como WebP e AVIF comprimem melhor que JPEG/PNG para o mesmo nível de qualidade visual, gerando arquivos bem menores.
  • Dimensão real de exibição: uma imagem de 4000px de largura exibida num espaço de 400px desperdiça 10x o dado necessário — redimensionar a imagem para o tamanho real de exibição (ou usar srcset para servir tamanhos diferentes por dispositivo) evita esse desperdício.
  • Compressão: ferramentas de compressão (com ou sem perda perceptível de qualidade) frequentemente cortam 50-80% do peso do arquivo original exportado direto de uma câmera ou editor de imagem.
<!-- srcset: o navegador escolhe a imagem mais adequada pro tamanho de tela do dispositivo -->
<img
  src="produto-800.jpg"
  srcset="produto-400.jpg 400w, produto-800.jpg 800w, produto-1600.jpg 1600w"
  sizes="(max-width: 600px) 400px, 800px"
  alt="Foto do produto"
/>

Minificação e bundling (conceitual)

Código-fonte de verdade é escrito pensando em quem vai ler (nomes descritivos, espaçamento, comentários) — mas o navegador não precisa de nada disso para executar o código, só precisa que ele funcione. Minificação é o processo automático que remove espaços em branco, encurta nomes de variáveis internas e elimina comentários do código antes de ele ser enviado ao navegador, reduzindo o peso do arquivo sem mudar seu comportamento. 

// Antes da minificação (código-fonte, legível)
function calcularTotalDoCarrinho(itens) {
  let total = 0;
  for (const item of itens) {
    total = total + item.preco * item.quantidade;
  }
  return total;
}

// Depois da minificação (o que realmente vai pro navegador)
function calcularTotalDoCarrinho(e){let t=0;for(const r of e)t+=r.preco*r.quantidade;return t}

Já bundling é o processo de juntar vários arquivos JavaScript/CSS separados (que existem como arquivos individuais durante o desenvolvimento, para facilitar a organização) num número menor de arquivos finais. Isso reduz a quantidade de requisições HTTP separadas que o navegador precisa fazer para buscar cada arquivo — historicamente uma otimização importante, e ainda relevante mesmo com HTTP/2 permitindo múltiplas requisições em paralelo mais eficientemente. Ferramentas como Vite, Webpack e esbuild fazem esse trabalho de minificação e bundling automaticamente como parte do processo de build, então na prática você raramente faz isso manualmente — mas entender o que acontece por trás ajuda a interpretar configurações de build e diagnosticar por que um bundle ficou grande demais.

Core Web Vitals: como o Google mede "rápido"

O Google definiu um conjunto de métricas chamado Core Web Vitals para quantificar a experiência real de carregamento e interação de uma página, do ponto de vista de quem está usando o site (não só "quanto tempo o servidor demorou para responder"). As três principais:

  • LCP (Largest Contentful Paint): quanto tempo até o maior elemento visível da tela (geralmente uma imagem ou bloco de texto principal) aparecer na tela. Mede a percepção de "a página carregou".
  • INP (Interaction to Next Paint): quanto tempo entre o usuário clicar/tocar em algo e a tela responder visualmente a essa ação. Mede a sensação de "o site está travado ou responsivo".
  • CLS (Cumulative Layout Shift): o quanto os elementos da página "pulam de lugar" durante o carregamento (por exemplo, um anúncio que carrega depois e empurra o texto que você estava lendo). Mede a estabilidade visual.

Você não precisa decorar as fórmulas exatas dessas métricas — o importante é entender a ideia por trás de cada uma, porque elas guiam diretamente as práticas anteriores: lazy loading e otimização de imagens melhoram o LCP, minificação e bundling reduzem o tempo até o JavaScript ficar pronto (o que ajuda no INP), e reservar espaço fixo para imagens (com atributos width/height) evita quedas de CLS.

Dica As ferramentas de desenvolvedor do próprio navegador (aba "Lighthouse" no Chrome DevTools, ou o site PageSpeed Insights do Google) medem essas métricas automaticamente e apontam, na prática, qual otimização traria mais ganho para uma página específica — é sempre melhor medir antes de otimizar às cegas.
Atenção Lazy loading aplicado à primeira imagem visível da tela (a que aparece assim que a página abre, sem precisar rolar) é contraproducente: em vez de acelerar, você atrasa justamente o elemento que define o LCP, porque o navegador só começa a buscá-lo depois de descobrir que ele está na tela. A regra prática é: lazy loading para o que está "abaixo da dobra" (fora da área visível inicial), carregamento imediato e priorizado para o que aparece assim que a página abre.

Resumo

  • Lazy loading adia o carregamento de imagens e componentes até o momento em que realmente serão exibidos.
  • Formato certo, dimensão de exibição real e compressão reduzem drasticamente o peso de imagens.
  • Minificação remove excesso do código para o navegador; bundling reduz a quantidade de arquivos separados.
  • Core Web Vitals (LCP, INP, CLS) medem a experiência real de carregamento, resposta e estabilidade visual.
  • Lazy loading deve poupar o que está fora da tela inicial — aplicado ao conteúdo visível de imediato, atrapalha o LCP.
