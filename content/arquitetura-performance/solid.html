10. Arquitetura & Performance

Princípios SOLID

Cinco ideias que, juntas, ajudam a manter um sistema fácil de mudar mesmo depois que ele cresce e ganha dezenas de arquivos e desenvolvedores.

Analogia Pense numa casa bem projetada versus uma reforma feita "na marra". Numa casa bem projetada, o encanamento fica dentro das paredes com pontos de acesso previstos, a fiação elétrica segue um padrão, e trocar uma torneira não exige quebrar o chão da cozinha inteira. Numa reforma malfeita, tudo está entrelaçado: mexer na tomada da sala derruba a energia do quarto, e trocar um cano obriga a arrancar o piso todo. SOLID é um conjunto de boas práticas de "encanamento" para código: se cada parte tem uma responsabilidade clara e pontos de conexão bem definidos, você consegue trocar uma peça sem que a casa inteira desabe.

SOLID é um acrônimo criado a partir de cinco princípios de design orientado a objetos, popularizados por Robert C. Martin ("Uncle Bob"). Eles não são leis matemáticas — são heurísticas, atalhos de experiência coletiva que ajudam a evitar armadilhas comuns de acoplamento e rigidez. Vamos ver os cinco, um a um, com analogia e código.

S — Single Responsibility Principle (Princípio da Responsabilidade Única)

Uma classe (ou módulo) deve ter um único motivo para mudar. Se uma classe mistura regra de negócio, acesso a banco de dados e formatação de e-mail, ela vai precisar ser alterada por três motivos completamente diferentes — e cada alteração corre o risco de quebrar as outras responsabilidades sem querer. 

// Ruim: uma classe com três motivos para mudar
class Funcionario {
  calcularSalario() { /* regra de negócio */ }
  salvarNoBanco() { /* acesso a dados */ }
  gerarReciboPdf() { /* geração de relatório */ }
}

// Melhor: cada responsabilidade em sua própria classe
class Funcionario {
  calcularSalario() { /* só regra de negócio */ }
}

class FuncionarioRepository {
  salvar(funcionario) { /* só acesso a dados */ }
}

class ReciboPdfGenerator {
  gerar(funcionario) { /* só geração de PDF */ }
}

Se amanhã trocar o banco de dados de MySQL para PostgreSQL, você mexe só em FuncionarioRepository. Se mudar o layout do recibo, mexe só em ReciboPdfGenerator. A classe Funcionario nem percebe essas mudanças.

O — Open/Closed Principle (Aberto/Fechado)

Uma entidade de código deve estar aberta para extensão, mas fechada para modificação. Na prática: quando surge um caso novo, você deveria conseguir adicionar código novo em vez de ficar reabrindo e editando uma função que já funciona (e já foi testada) para enfiar mais um if nela. 

// Ruim: toda vez que surge uma forma de pagamento nova, essa função precisa ser editada
function calcularTaxa(formaPagamento, valor) {
  if (formaPagamento === "cartao") return valor * 0.03;
  if (formaPagamento === "boleto") return valor * 0.01;
  if (formaPagamento === "pix") return 0;
  // daqui a um mês: "if (formaPagamento === 'cripto') ..."
}

// Melhor: cada forma de pagamento é uma implementação própria, plugável
class TaxaCartao {
  calcular(valor) { return valor * 0.03; }
}
class TaxaBoleto {
  calcular(valor) { return valor * 0.01; }
}
class TaxaPix {
  calcular(valor) { return 0; }
}

function calcularTaxa(estrategiaTaxa, valor) {
  return estrategiaTaxa.calcular(valor);
}

// Para adicionar cripto, basta criar uma nova classe, sem tocar em calcularTaxa
class TaxaCripto {
  calcular(valor) { return valor * 0.015; }
}

A função calcularTaxa nunca mais precisa ser reaberta: novas formas de pagamento chegam como código novo, não como edições em código antigo que já funcionava.

L — Liskov Substitution Principle (Substituição de Liskov)

Se uma classe B herda de uma classe A, você deveria poder usar um objeto B em qualquer lugar que espera um A, sem que o programa quebre ou se comporte de forma inesperada. O exemplo clássico (e um pouco contraintuitivo) é o de retângulos e quadrados. 

// Ruim: Quadrado "herda" de Retangulo, mas quebra a expectativa de quem usa Retangulo
class Retangulo {
  setLargura(l) { this.largura = l; }
  setAltura(a) { this.altura = a; }
  area() { return this.largura * this.altura; }
}

class Quadrado extends Retangulo {
  setLargura(l) { this.largura = l; this.altura = l; } // efeito colateral inesperado!
  setAltura(a) { this.altura = a; this.largura = a; }
}

function testarArea(retangulo) {
  retangulo.setLargura(5);
  retangulo.setAltura(10);
  console.log(retangulo.area()); // espera 50, mas se for um Quadrado, dá 100
}

Quem escreveu testarArea confiava que "setar largura" não mudaria a altura — uma suposição razoável para qualquer Retangulo. Mas Quadrado quebra essa suposição, então ele não é um substituto seguro. A correção geralmente não é "consertar" a herança, e sim perceber que Quadrado não deveria herdar de Retangulo — os dois deveriam implementar uma interface comum Forma, sem uma fingir ser a outra.

I — Interface Segregation Principle (Segregação de Interfaces)

É melhor ter várias interfaces pequenas e específicas do que uma única interface enorme que obriga quem a implementa a lidar com métodos que nunca vai usar. 

// Ruim: uma interface "genérica demais" para todo tipo de trabalhador
interface Trabalhador {
  trabalhar();
  almocar();
  receberSalario();
}

// Um robô que "trabalha" é forçado a implementar "almocar", que não faz sentido pra ele
class RoboMontador implements Trabalhador {
  trabalhar() { /* ok */ }
  almocar() { throw new Error("Robôs não almoçam"); } // gambiarra forçada pela interface
  receberSalario() { throw new Error("Robôs não recebem salário"); }
}

// Melhor: interfaces menores e específicas
interface PodeTrabalhar { trabalhar(); }
interface PodeAlmocar { almocar(); }
interface RecebeSalario { receberSalario(); }

class RoboMontador implements PodeTrabalhar {
  trabalhar() { /* só o que faz sentido para um robô */ }
}

class FuncionarioHumano implements PodeTrabalhar, PodeAlmocar, RecebeSalario {
  trabalhar() { /* ... */ }
  almocar() { /* ... */ }
  receberSalario() { /* ... */ }
}

Cada classe implementa só as interfaces que fazem sentido pra ela, sem métodos vazios ou que lançam erro só para "cumprir tabela".

D — Dependency Inversion Principle (Inversão de Dependência)

Módulos de alto nível (regras de negócio) não deveriam depender diretamente de módulos de baixo nível (detalhes técnicos, como qual banco de dados ou qual serviço de e-mail está sendo usado). Ambos deveriam depender de uma abstração (uma interface) — assim, trocar o detalhe técnico não exige tocar na regra de negócio. 

// Ruim: a regra de negócio depende diretamente de um serviço concreto
class NotificadorPedido {
  constructor() {
    this.emailService = new EmailGmailService(); // acoplado a uma implementação específica
  }
  notificar(pedido) {
    this.emailService.enviar(pedido.clienteEmail, "Seu pedido foi confirmado!");
  }
}

// Melhor: a regra de negócio depende de uma abstração (interface), não de um serviço específico
class NotificadorPedido {
  constructor(servicoDeNotificacao) { // qualquer coisa que "sabe notificar"
    this.servicoDeNotificacao = servicoDeNotificacao;
  }
  notificar(pedido) {
    this.servicoDeNotificacao.enviar(pedido.clienteEmail, "Seu pedido foi confirmado!");
  }
}

// Hoje pode ser e-mail, amanhã pode ser SMS ou WhatsApp, sem mudar NotificadorPedido
const notificador = new NotificadorPedido(new EmailGmailService());
// ou
const notificadorSms = new NotificadorPedido(new SmsTwilioService());

Essa técnica de "passar a dependência de fora" se chama injeção de dependência, e é a forma prática mais comum de aplicar esse princípio no dia a dia.

Dica Uma boa forma de perceber violações de SOLID sem decorar as cinco letras: pergunte "se eu precisar trocar só essa peça (o banco, o serviço de e-mail, a regra de desconto), quantos arquivos eu preciso abrir?". Se a resposta for "vários, e nem todos óbvios", provavelmente há um princípio sendo violado ali.
Atenção — over-engineering SOLID é uma ferramenta para gerenciar a complexidade de sistemas que crescem, não um checklist obrigatório para todo pedaço de código. Criar uma interface, uma injeção de dependência e três camadas de abstração para uma função que soma dois números e nunca vai mudar é over-engineering: você paga o custo de complexidade extra sem nunca colher o benefício de flexibilidade. Aplique SOLID onde existe variação real esperada (várias formas de pagamento, vários bancos de dados possíveis, regras de negócio que mudam com frequência) — não em cada classe do projeto por precaução.

Resumo

  • S — cada classe deve ter um único motivo para mudar.
  • O — extensível com código novo, sem precisar reabrir e editar código que já funciona.
  • L — uma subclasse deve poder substituir a classe-mãe sem surpresas de comportamento.
  • I — prefira várias interfaces pequenas e específicas a uma única interface genérica e inchada.
  • D — regras de negócio devem depender de abstrações, não de implementações técnicas concretas.
  • SOLID resolve dor de sistemas que crescem e mudam; aplicado sem necessidade, vira over-engineering.
