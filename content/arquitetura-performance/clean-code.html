10. Arquitetura & Performance

Clean Code

Código funciona quando o computador entende. Código limpo funciona quando o próximo humano também entende — e esse humano, quase sempre, é você mesmo daqui a seis meses.

Analogia Imagine duas cozinhas de restaurante. Na primeira, cada tempero está num pote rotulado, os utensílios ficam sempre no mesmo gancho, e qualquer cozinheiro novo consegue montar um prato em cinco minutos só olhando a organização. Na segunda, tudo funciona — a comida sai gostosa — mas só o chef original sabe onde está cada coisa, por que o sal fica ao lado do açúcar e o que significa aquele post-it colado no forno. As duas cozinhas produzem o mesmo prato hoje. Só uma delas continua funcionando quando o chef tira férias, contrata alguém novo, ou quando o cardápio precisa mudar às pressas. Clean code é a primeira cozinha: código que continua sendo modificável mesmo depois que a pressa e a memória de curto prazo de quem escreveu já se foram.

"Clean Code" não é um conjunto de regras rígidas — é um objetivo: escrever código que comunica sua intenção sem exigir que o leitor rode o programa mentalmente para entender o que ele faz. Todo código será lido muito mais vezes do que será escrito: você escreve uma função uma vez, mas ela vai ser lida em cada revisão de código, em cada debug, em cada nova funcionalidade que passar perto dela. Investir um pouco mais de cuidado agora economiza muito mais tempo depois.

Nomes bons contam a história sozinhos

O nome de uma variável, função ou classe é a primeira (e às vezes única) documentação que alguém vai ler. Um nome ruim obriga o leitor a abrir a implementação para entender o que a coisa faz; um nome bom elimina essa necessidade na maior parte do tempo. 

// Ruim: o que é "d"? dias? distância? desconto?
function calc(d, p) {
  return p - (p * d / 100);
}

// Bom: o nome já responde "o que isso calcula"
function calcularPrecoComDesconto(percentualDesconto, precoOriginal) {
  return precoOriginal - (precoOriginal * percentualDesconto / 100);
}

Repare que o segundo exemplo é mais longo — e está certo que esteja. Nomes curtos só valem a pena quando o escopo é minúsculo (um índice i num laço de três linhas, por exemplo). Fora isso, prefira um nome específico e um pouco mais longo a um nome genérico e curto. Boas perguntas para testar um nome:

  • Funções: o nome deveria ser um verbo que descreve exatamente a ação (enviarEmail, validarCpf, buscarUsuarioPorId).
  • Variáveis e booleanos: nomes que soam como perguntas de sim/não ajudam muito (estaAtivo, temPermissao, podeEditar).
  • Evite abreviações obscuras. qtdItensCarr economiza cinco caracteres e custa cinco segundos de confusão a cada leitura.

Funções pequenas, com uma única responsabilidade

Uma função deveria fazer uma coisa, fazer bem, e ter um nome que descreva exatamente essa coisa. Quando uma função mistura várias responsabilidades — validar, calcular, salvar no banco e enviar e-mail, tudo junto — ela fica difícil de testar, difícil de reaproveitar e difícil de entender de relance. 

// Ruim: uma função fazendo cinco coisas diferentes
function finalizarPedido(pedido) {
  if (!pedido.itens || pedido.itens.length === 0) {
    throw new Error("Pedido vazio");
  }
  let total = 0;
  for (const item of pedido.itens) {
    total += item.preco * item.quantidade;
  }
  if (pedido.cupom) {
    total = total * 0.9;
  }
  db.salvar("pedidos", { ...pedido, total });
  emailService.enviar(pedido.clienteEmail, "Pedido confirmado!");
  return total;
}

// Melhor: cada função tem uma única responsabilidade
function validarPedido(pedido) {
  if (!pedido.itens || pedido.itens.length === 0) {
    throw new Error("Pedido vazio");
  }
}

function calcularTotal(pedido) {
  const subtotal = pedido.itens.reduce((soma, item) => soma + item.preco * item.quantidade, 0);
  return pedido.cupom ? subtotal * 0.9 : subtotal;
}

function finalizarPedido(pedido) {
  validarPedido(pedido);
  const total = calcularTotal(pedido);
  db.salvar("pedidos", { ...pedido, total });
  emailService.enviar(pedido.clienteEmail, "Pedido confirmado!");
  return total;
}

A versão dividida é mais fácil de testar isoladamente (você pode testar calcularTotal sem precisar de um banco de dados de verdade), mais fácil de reaproveitar (talvez outro fluxo também precise calcular o total sem finalizar o pedido) e a função finalizarPedido virou quase uma frase em português: valida, calcula, salva, envia e-mail.

Uma regra prática (não uma lei absoluta): se você precisa usar a palavra "e" para descrever o que uma função faz ("valida e calcula e salva"), ela provavelmente deveria ser dividida.

Dica Um sinal prático de que uma função está fazendo coisa demais: o tamanho da indentação. Muitos níveis de if, for aninhados dentro de if costumam indicar que ali dentro cabem duas ou três funções menores, cada uma com seu próprio nome.

Comentários: o último recurso, não o primeiro

Existe uma armadilha comum: achar que código bem comentado é sinônimo de código limpo. Na prática, o comentário mais perigoso é aquele que descreve o que o código faz — porque o código já diz isso, e o comentário só corre o risco de ficar desatualizado quando o código mudar e ninguém lembrar de atualizar o texto ao lado. 

// Ruim: o comentário só repete o código, e ainda pode "mentir" no futuro
// incrementa o contador em 1
contador = contador + 1;

// Ruim: o comentário existe porque o código não é claro
// verifica se usuário pode comprar (tem mais de 18 e não está bloqueado)
if (u.idade >= 18 && !u.bloq) { ... }

// Bom: o próprio código já é a explicação
const podeComprar = usuario.idade >= 18 && !usuario.estaBloqueado;
if (podeComprar) { ... }

Isso não significa "nunca comente nada". Comentários continuam valiosos para explicar o por quê de uma decisão que não é óbvia pelo código — uma regra de negócio estranha exigida por um cliente, uma limitação de uma API externa, um workaround temporário para um bug de terceiros. O teste é simples: se o comentário pode ser substituído por um nome melhor de variável ou função, ele deveria ser. Se ele explica um "porquê" que não existe em lugar nenhum do código, ele deveria ficar.

DRY na prática (sem virar obsessão)

DRY significa "Don't Repeat Yourself" — não repita a si mesmo. A ideia central é que cada pedaço de conhecimento sobre o sistema (uma regra de negócio, uma fórmula, uma validação) deveria existir em um único lugar no código. Quando a mesma lógica está copiada e colada em três arquivos diferentes, um dia alguém vai corrigir um bug em um dos três e esquecer os outros dois — e agora o sistema tem um comportamento inconsistente e difícil de rastrear. 

// Ruim: a regra "desconto de 10% com cupom" está duplicada
function totalCarrinho(itens, temCupom) {
  let total = itens.reduce((s, i) => s + i.preco, 0);
  if (temCupom) total = total * 0.9;
  return total;
}

function totalAssinatura(valorMensal, temCupom) {
  let total = valorMensal;
  if (temCupom) total = total * 0.9; // mesma regra, copiada aqui de novo
  return total;
}

// Melhor: a regra existe em um único lugar
function aplicarDesconto(valor, temCupom) {
  return temCupom ? valor * 0.9 : valor;
}

function totalCarrinho(itens, temCupom) {
  const total = itens.reduce((s, i) => s + i.preco, 0);
  return aplicarDesconto(total, temCupom);
}

function totalAssinatura(valorMensal, temCupom) {
  return aplicarDesconto(valorMensal, temCupom);
}
Atenção DRY é sobre conhecimento repetido, não sobre texto parecido. Duas funções que parecem similares hoje mas representam regras de negócio diferentes (o desconto de cliente novo e o desconto de Black Friday, por exemplo) não deveriam ser fundidas numa função só só porque o código é parecido — se amanhã uma regra mudar e a outra não, você vai precisar desfazer a fusão às pressas. Extrair uma abstração compartilhada cedo demais, para coisas que só coincidem por acaso, costuma criar mais confusão do que resolver. Prefira duplicar uma vez e observar se a duplicação realmente representa a mesma regra antes de unificar.

Juntando tudo: um exemplo antes e depois

// Antes
function proc(u) {
  if (u.a >= 18) {
    if (u.doc && u.doc.length === 11) {
      let x = 0;
      for (let i = 0; i < u.compras.length; i++) {
        x += u.compras[i].v;
      }
      return x > 1000 ? x * 0.95 : x;
    }
  }
  return 0;
}

// Depois
function ehMaiorDeIdade(usuario) {
  return usuario.idade >= 18;
}

function temCpfValido(usuario) {
  return Boolean(usuario.cpf) && usuario.cpf.length === 11;
}

function calcularTotalCompras(usuario) {
  return usuario.compras.reduce((total, compra) => total + compra.valor, 0);
}

function aplicarDescontoPorVolume(total) {
  const LIMITE_PARA_DESCONTO = 1000;
  const PERCENTUAL_DESCONTO = 0.95;
  return total > LIMITE_PARA_DESCONTO ? total * PERCENTUAL_DESCONTO : total;
}

function calcularTotalElegivel(usuario) {
  if (!ehMaiorDeIdade(usuario) || !temCpfValido(usuario)) {
    return 0;
  }
  const total = calcularTotalCompras(usuario);
  return aplicarDescontoPorVolume(total);
}

A segunda versão tem mais linhas — mas cada função é lida em segundos, tem um nome que já explica o que ela faz, e pode ser testada isoladamente. Esse é o núcleo de clean code: trocar "linhas de código mais curtas" por "tempo de leitura mais curto".

Resumo

  • Nomes bons eliminam a necessidade de ler a implementação para entender a intenção.
  • Funções pequenas com uma única responsabilidade são mais fáceis de testar, ler e reaproveitar.
  • Comentários devem explicar o "porquê", não o "o quê" — o código já deveria dizer o "o quê" sozinho.
  • DRY é sobre não duplicar conhecimento (regras de negócio), não sobre evitar qualquer texto parecido.
  • Unificar código parecido cedo demais, sem confirmar que é a mesma regra, cria acoplamento indevido.
