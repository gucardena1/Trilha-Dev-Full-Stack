4. Git & GitHub

Boas práticas de commits

Refinando hábitos: como escrever commits que seu "eu do futuro" (e sua equipe) vão agradecer.

Analogia Pense no histórico de commits de um projeto como o diário de bordo de um navio. Um bom diário de bordo registra, de forma objetiva e datada, exatamente o que aconteceu em cada trecho da viagem — "às 14h, ajustamos o curso 5 graus a leste por causa de uma corrente" — permitindo que qualquer tripulante, mesmo anos depois, entenda o que aconteceu e por quê. Um diário de bordo ruim só diria "coisas aconteceram" em toda página. Commits são o diário de bordo do seu código.

Se você chegou até aqui, já sabe usar Git no dia a dia: cria branches, resolve conflitos, abre pull requests. Esta lição não ensina comandos novos — ela é sobre refinar hábitos. A diferença entre um repositório fácil de entender daqui a um ano e um repositório indecifrável quase sempre está nos detalhes que vamos ver agora.

Mensagens de commit: boas vs. ruins

Compare estas duas mensagens de commit para a mesma mudança: 

fix
mudanças
wip
asdkjasd
teste

contra: 

Corrige cálculo de frete para pedidos com mais de 10kg

O arredondamento estava truncando o peso antes de aplicar a
tabela de faixas, fazendo pedidos de 10,4kg caírem na faixa
de até 10kg. Agora o arredondamento acontece só na exibição.

A primeira mensagem não diz nada — daqui a três meses, ninguém (nem quem escreveu) vai saber o que "mudanças" significa sem abrir o commit inteiro e tentar adivinhar pelo código. A segunda mensagem conta uma história: o que foi corrigido, qual era a causa raiz do problema e o que mudou para resolvê-lo. Um bom padrão para seguir é: primeira linha curta (até ~50 caracteres) no imperativo ("corrige", "adiciona", "remove" — não "corrigido" ou "corrigindo"), seguida de uma linha em branco e, se necessário, um corpo explicando o contexto e o motivo.

Dica Um teste rápido para saber se sua mensagem de commit está boa: complete a frase "Se aplicado, este commit vai ___________". Se a mensagem encaixa naturalmente ali ("vai corrigir cálculo de frete para pedidos com mais de 10kg"), está no caminho certo. Se a mensagem for "fix" ou "mudanças", a frase não faz sentido nenhum.

Commits pequenos e atômicos

Um commit atômico é aquele que representa uma única mudança lógica e completa — se você precisasse desfazer só aquele commit (com git revert, por exemplo), o projeto continuaria funcionando de forma coerente, sem deixar a metade de uma funcionalidade pelo caminho. Evite misturar, num único commit, uma correção de bug com uma refatoração de estilo de código e a adição de uma funcionalidade nova — cada uma dessas coisas deveria ser seu próprio commit.

As vantagens de commits pequenos e focados aparecem principalmente quando algo dá errado: fica muito mais fácil usar git log para encontrar exatamente quando um bug foi introduzido, e muito mais seguro reverter só aquela mudança específica sem afetar o resto. Um commit gigante que mistura vinte coisas diferentes é praticamente impossível de reverter parcialmente.

Atenção Commits atômicos não significam commits minúsculos demais a ponto de deixarem o projeto quebrado entre um commit e outro (por exemplo, um commit que só adiciona metade de uma função, sem ela funcionar ainda). O critério é lógico, não de tamanho: cada commit deve deixar o projeto num estado coerente, mesmo que pequeno.

Conventional Commits: um padrão para o prefixo da mensagem

Muitas equipes adotam um padrão chamado Conventional Commits, que prefixa a primeira linha da mensagem com uma palavra-chave indicando o tipo de mudança. Isso padroniza o histórico e permite até automatizar coisas como a geração de changelogs. O formato básico é: 

tipo(escopo opcional): descrição curta no imperativo

Os tipos mais comuns são:

  • feat: uma funcionalidade nova (ex: feat(carrinho): adiciona cupom de desconto)
  • fix: uma correção de bug (ex: fix(frete): corrige arredondamento de peso)
  • docs: mudanças só em documentação
  • style: formatação, espaçamento, ponto e vírgula — sem alterar comportamento
  • refactor: reorganização do código sem mudar o comportamento externo
  • test: adição ou ajuste de testes
  • chore: tarefas de manutenção (atualizar dependências, configurar ferramentas)
git commit -m "fix(auth): impede login com senha vazia"
git commit -m "feat(perfil): adiciona upload de foto de usuário"
git commit -m "chore(deps): atualiza versão do axios"

.gitignore: o que nunca deveria virar commit

Nem tudo dentro da pasta do projeto deveria entrar no repositório. Dependências instaladas (como a pasta node_modules), arquivos gerados automaticamente (builds, caches), arquivos de configuração da sua máquina (como .env com senhas e chaves de API) e arquivos do seu editor não devem ser versionados — eles são grandes, mudam constantemente sem relevância nenhuma para o histórico, e no caso de senhas, representam um risco de segurança real se forem parar num repositório público.

O arquivo .gitignore, na raiz do projeto, lista padrões de arquivos e pastas que o Git deve simplesmente ignorar, nunca sugerindo adicioná-los: 

# .gitignore
node_modules/
.env
dist/
*.log
.DS_Store
Atenção Se um arquivo sensível (como .env) já foi commitado antes de você adicionar o .gitignore, apenas adicioná-lo ao .gitignore não remove o arquivo do histórico — ele continua lá, em commits antigos, acessível a qualquer pessoa com acesso ao repositório. Nesse caso é preciso removê-lo do histórico com ferramentas específicas (como git filter-repo) e, o mais importante, trocar imediatamente qualquer senha ou chave que tenha vazado.

Quando (não) usar --force

O comando git push --force sobrescreve o histórico do repositório remoto com o seu histórico local, mesmo que eles tenham divergido — é uma operação destrutiva, porque pode apagar commits que outras pessoas já enviaram e que você simplesmente não tem localmente. Existem usos legítimos, principalmente quando você reorganiza o histórico da sua própria branch pessoal, que mais ninguém está usando, antes de abrir um pull request: 

# Mais seguro que --force: falha se alguém mais mudou a branch remota
git push --force-with-lease origin minha-branch-pessoal

A regra prática é simples: nunca faça force push em branches compartilhadas, e principalmente nunca na main ou em qualquer branch que outras pessoas também estejam usando. Se você sobrescrever o histórico remoto de uma branch em que outra pessoa também trabalha, o próximo git pull dela vai gerar um estado confuso, e commits que ela já tinha podem simplesmente desaparecer do remoto sem aviso.

Dica A maioria dos projetos sérios configura proteções na branch main no próprio GitHub, impedindo fisicamente qualquer force push nela, mesmo por engano. Se você tem acesso de administrador a um repositório de equipe, vale a pena habilitar essa proteção logo no início do projeto.

Resumo

  • Mensagens de commit devem explicar o "porquê", não só repetir o óbvio ("fix", "mudanças").
  • Commits atômicos representam uma única mudança lógica e coerente, facilitando reverter e depurar.
  • Conventional Commits padroniza mensagens com prefixos como feat:, fix:, chore:.
  • O .gitignore impede que dependências, builds e segredos entrem no repositório.
  • Force push nunca deve ser usado em branches compartilhadas, especialmente a main; prefira --force-with-lease quando realmente necessário.
