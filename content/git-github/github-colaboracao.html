4. Git & GitHub

GitHub: pull requests e code review

Como equipes de verdade usam o GitHub para revisar código antes de juntá-lo ao projeto.

Analogia Pense num artigo enviado para uma revista científica. O autor não simplesmente publica o texto direto — ele envia para revisores, que leem com calma, apontam problemas, sugerem melhorias e só aprovam a publicação depois que tudo estiver adequado. Um pull request no GitHub é exatamente esse processo aplicado a código: antes de uma mudança entrar na versão principal do projeto, ela passa por uma revisão formal de outras pessoas da equipe.

Nas lições anteriores você aprendeu Git puro: repositórios, commits, branches, merges. Tudo isso funciona perfeitamente sozinho, no seu computador. O GitHub entra em cena quando várias pessoas precisam colaborar de forma organizada — e é aí que aparecem conceitos que não existem no Git em si, mas sim como recursos que o GitHub adiciona por cima dele.

Git x GitHub: reforçando a diferença

Vale reforçar, porque é uma confusão muito comum: Git é o programa que roda no seu computador e controla versões de arquivos — ele existiria e funcionaria perfeitamente mesmo sem internet. GitHub é um site (de propriedade da Microsoft) que hospeda repositórios Git na nuvem e adiciona uma camada de colaboração em cima deles: interface visual, pull requests, issues, revisão de código, automações, e muito mais. Existem alternativas ao GitHub — GitLab e Bitbucket, por exemplo — que também hospedam repositórios Git e oferecem recursos parecidos, mas com nomes um pouco diferentes.

Fork vs. branch: dois jeitos de "ter sua própria cópia"

Quando você quer contribuir com um projeto, existem dois cenários diferentes, com soluções diferentes:

  • Branch: usada quando você já tem permissão de escrita no repositório (por exemplo, é funcionário da empresa dona do projeto). Você cria uma branch nova dentro do mesmo repositório, trabalha nela e depois abre um pull request para juntá-la à main.
  • Fork: usado quando você não tem permissão de escrita — por exemplo, ao contribuir com um projeto de código aberto de terceiros. Um fork cria uma cópia completa e independente do repositório na sua própria conta do GitHub. Você faz as mudanças no seu fork e, quando estiver pronto, abre um pull request pedindo para que o dono do projeto original traga suas mudanças de volta.

Em resumo: branch é para trabalhar dentro de um repositório que você já tem acesso; fork é para criar sua própria cópia de um repositório que você não controla, para depois propor as mudanças de volta.

Criando um pull request

Depois de criar uma branch, fazer commits nela e enviá-la para o GitHub com git push, o próprio GitHub costuma exibir um botão sugerindo "Compare & pull request". O processo, de forma resumida: 

git checkout -b corrige-calculo-frete
# ... edita os arquivos, testa ...
git add .
git commit -m "Corrige arredondamento no cálculo de frete"
git push origin corrige-calculo-frete

A partir daí, no site do GitHub, você abre um pull request (também chamado de PR) escolhendo qual branch quer juntar (a sua) e em qual branch ela deve entrar (geralmente a main). Um bom PR inclui:

  • Um título claro, resumindo o que foi feito.
  • Uma descrição explicando o "porquê" da mudança, não só o "o quê" — o código já mostra o que mudou, a descrição deveria explicar o motivo e qualquer contexto necessário para entender.
  • Referência a alguma issue relacionada, se existir (ex: "Resolve #42").
  • Se fizer sentido, prints de tela, vídeos curtos ou instruções de como testar a mudança.
Dica Pull requests pequenos e focados numa única mudança são muito mais fáceis de revisar do que um PR gigante misturando dez coisas diferentes. Um revisor cansado, olhando 2000 linhas alteradas de uma vez, tende a aprovar rápido demais só para "se livrar" da revisão — o que anula o próprio propósito do processo.

O que revisar num code review

Revisar código de outra pessoa (ou pedir para revisarem o seu) é uma das atividades mais importantes do trabalho em equipe, e vai muito além de só procurar erros de sintaxe. Alguns pontos que um bom revisor costuma observar:

  • Corretude: o código realmente faz o que a descrição do PR diz que faz? Existem casos extremos (entradas vazias, números negativos, listas vazias) que não foram considerados?
  • Legibilidade: outra pessoa, sem contexto nenhum, conseguiria entender esse código só de lê-lo? Nomes de variáveis e funções fazem sentido?
  • Consistência: o código segue os padrões e convenções já usados no resto do projeto?
  • Testes: existem testes cobrindo a nova funcionalidade ou a correção do bug? (Assunto de uma trilha própria sobre testes.)
  • Escopo: o PR faz só o que se propõe a fazer, sem misturar mudanças não relacionadas?
  • Segurança e desempenho: a mudança introduz algum risco óbvio, como dados sensíveis expostos ou uma operação lenta demais rodando repetidamente?

Um bom feedback de code review é específico e educado — em vez de "isso está errado", algo como "acho que esse laço pode falhar se a lista vier vazia, já testou esse caso?" abre uma conversa em vez de soar como uma crítica pessoal.

Issues: organizando o que precisa ser feito

Uma issue (item, em inglês) é um registro no GitHub descrevendo um problema a resolver ou uma funcionalidade a construir — como um cartão num quadro de tarefas. Issues podem ter descrição detalhada, responsáveis atribuídos, etiquetas (como "bug", "melhoria", "urgente") e comentários de discussão. Um pull request pode referenciar uma issue diretamente na descrição, usando palavras como Closes #42 ou Resolve #42 — quando esse PR for juntado à main, o GitHub fecha automaticamente a issue correspondente.

Atenção Um erro comum de quem está começando é abrir um pull request enorme, sem descrição nenhuma, direto contra a main de um projeto importante. Antes de abrir um PR, sempre confira: a branch está atualizada com a main (rode um git pull nela antes)? O escopo está pequeno e focado? A descrição explica o "porquê"? Isso poupa tempo seu e de quem vai revisar.

Resumo

  • Git controla versões no seu computador; GitHub hospeda repositórios na nuvem e adiciona colaboração.
  • Branch é para quem já tem acesso ao repositório; fork cria uma cópia própria para quem não tem.
  • Um pull request (PR) propõe formalmente juntar uma branch a outra, geralmente com revisão antes.
  • Um bom code review olha corretude, legibilidade, consistência, testes, escopo e segurança.
  • Issues organizam tarefas e bugs, e podem ser fechadas automaticamente por um PR relacionado.
