4. Git & GitHub

Branches, merge e conflitos

Como trabalhar em algo novo sem bagunçar o que já funciona — e o que fazer quando duas mudanças colidem.

Analogia Imagine que você está escrevendo um livro e quer testar um final alternativo, sem estragar o final original caso a experiência não funcione. Você tira uma cópia do manuscrito, escreve o final alternativo nessa cópia, e só depois decide se junta essa versão nova ao manuscrito principal. Uma branch (galho, em inglês) é exatamente isso: uma linha do tempo paralela do seu projeto, onde você pode experimentar livremente sem afetar a versão principal, até decidir juntar ("merge") as duas de volta.

Até agora, todos os comandos que você aprendeu funcionavam numa única linha do tempo. Mas, na prática, projetos reais têm várias pessoas mexendo em partes diferentes ao mesmo tempo, e ninguém quer que uma funcionalidade pela metade quebre o que já está funcionando em produção. É exatamente para isso que existem as branches.

O que é uma branch, na prática

Toda repositório Git tem, desde o começo, pelo menos uma branch — geralmente chamada main (às vezes master, em projetos mais antigos). Essa costuma ser a linha do tempo "oficial", a versão estável do projeto. Quando você quer desenvolver algo novo — uma funcionalidade, uma correção de bug, um experimento — a prática recomendada é criar uma branch nova a partir da main, trabalhar nela isoladamente, e só depois juntá-la de volta. 

git branch                       # lista as branches existentes
git branch nova-funcionalidade   # cria uma branch nova (sem entrar nela ainda)
git checkout nova-funcionalidade # muda para a branch criada

# Ou, no mesmo comando, criar e já entrar:
git checkout -b nova-funcionalidade

# Em versões mais recentes do Git, o comando equivalente é:
git switch -c nova-funcionalidade

A partir do momento em que você está "dentro" de uma branch, todo commit que você criar fica registrado apenas nela — a main continua exatamente como estava, intocada, até que você decida juntar as duas.

Por que usar branches

As vantagens de trabalhar assim, em vez de commitar tudo direto na main, são várias:

  • Você pode experimentar e até "errar" sem risco de quebrar a versão estável do projeto.
  • Várias pessoas conseguem trabalhar em partes diferentes do projeto ao mesmo tempo, sem pisar no trabalho umas das outras.
  • Fica fácil abandonar uma ideia que não deu certo — basta simplesmente não juntar aquela branch, sem afetar nada.
  • No GitHub, cada branch pode virar um pull request — um pedido formal de revisão antes de entrar na main (assunto da próxima lição).

git merge: juntando duas linhas do tempo

Quando o trabalho numa branch está pronto, você volta para a branch que vai receber as mudanças (geralmente a main) e roda o comando merge, apontando qual branch entrar: 

git checkout main               # volta para a branch principal
git pull origin main            # garante que está atualizada
git merge nova-funcionalidade    # traz as mudanças da outra branch para cá

Na maioria das vezes, quando as duas branches mudaram partes diferentes do código, o Git consegue juntar tudo automaticamente, sem precisar de nenhuma intervenção sua. O problema aparece quando as duas branches mudaram a mesma linha do mesmo arquivo de formas diferentes — aí o Git não sabe qual versão manter, e é aí que surge um conflito de merge.

O que é um conflito de merge

Um conflito acontece quando o Git encontra duas mudanças concorrentes que ele não consegue decidir sozinho qual delas deve "vencer". Isso não é um erro nem um bug — é o Git sendo honesto: "não sei o que você quer aqui, decida por mim". Quando isso acontece, o Git marca o trecho conflitante diretamente dentro do arquivo, usando marcadores especiais: 

<<<<<<< HEAD
const saudacao = "Bom dia!";
=======
const saudacao = "Olá, tudo bem?";
>>>>>>> nova-funcionalidade

Tudo entre <<<<<<< HEAD e o separador ======= é a versão da branch em que você está agora; tudo entre o separador e >>>>>>> nova-funcionalidade é a versão que veio da outra branch.

Resolvendo um conflito, passo a passo

  1. Rode git status. Ele vai listar exatamente quais arquivos têm conflito, sob o título "Unmerged paths" (caminhos não mesclados).
  2. Abra cada arquivo listado no seu editor de código e procure pelos marcadores <<<<<<<, ======= e >>>>>>>.
  3. Decida qual versão deve ficar — pode ser uma das duas, uma combinação das duas, ou algo totalmente reescrito — e apague os marcadores manualmente, deixando o arquivo exatamente como ele deveria ficar.
  4. Repita para todos os arquivos em conflito. Salve todos eles.
  5. Marque os arquivos como resolvidos com git add, exatamente como faria com qualquer mudança: 
    git add src/mensagens.js
  6. Finalize o merge com um commit. O Git já sugere uma mensagem padrão, mas você pode ajustá-la: 
    git commit -m "Resolve conflito de mensagem de saudação"
Dica Se o conflito parecer grande demais ou você perceber que fez alguma bobagem no meio do processo, é seguro cancelar o merge inteiro com git merge --abort — isso devolve o repositório ao estado de antes de tentar juntar as branches, sem perder nada, para você tentar de novo com calma.
Atenção Nunca resolva um conflito "no susto", apagando um dos dois lados sem entender o que cada um fazia. Leia com calma o que a outra pessoa (ou você mesmo, em outra branch) estava tentando fazer — às vezes a solução correta é combinar as duas mudanças, não escolher uma e descartar a outra.

Resumo

  • Uma branch é uma linha do tempo paralela do projeto, isolada da branch principal (geralmente main).
  • git checkout -b nome (ou git switch -c nome) cria e entra numa branch nova.
  • git merge nome-da-branch junta as mudanças de outra branch na branch atual.
  • Um conflito de merge acontece quando duas branches mudam a mesma linha de formas diferentes.
  • Resolver um conflito é editar o arquivo manualmente, remover os marcadores e finalizar com add + commit.
