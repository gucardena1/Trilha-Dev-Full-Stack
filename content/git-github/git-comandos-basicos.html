4. Git & GitHub

Comandos essenciais do dia a dia

Os oito comandos que resolvem 90% do uso real do Git no dia a dia.

Analogia Pense no Git como uma mesa de trabalho com três áreas: a bagunça (os arquivos que você está editando agora), a caixa de "pronto para guardar" (o que você já revisou e decidiu incluir na próxima foto) e o álbum de fotos (o histórico permanente de commits). Os comandos que você vai aprender aqui servem, basicamente, para mover as coisas entre essas três áreas — e depois, para levar o álbum inteiro até um servidor remoto e trazer de volta o que outras pessoas adicionaram.

Na lição anterior você entendeu por que o Git existe. Agora é hora de colocar a mão no terminal. Não se preocupe em decorar tudo de uma vez — o objetivo aqui é entender o que cada comando faz e por que ele existe. Com a prática, eles viram automáticos.

git init: criando um repositório novo

Todo repositório Git começa com o comando git init, executado dentro da pasta do seu projeto. Ele cria a subpasta escondida .git, que é onde o Git vai guardar todo o histórico de commits daquele projeto. Você só roda esse comando uma vez, no início da vida do projeto. 

cd meu-projeto
git init
# Saída: Initialized empty Git repository in .../meu-projeto/.git/

git clone: copiando um repositório que já existe

Se o projeto já existe em algum lugar (por exemplo, no GitHub), você não usa git init — você usa git clone, passando o endereço do repositório. Isso baixa o projeto inteiro, com todo o histórico de commits, para uma pasta nova no seu computador, já configurada para conversar com aquele repositório remoto. 

git clone https://github.com/usuario/meu-projeto.git

git status: "em que ponto eu estou?"

Esse é, de longe, o comando que você vai rodar com mais frequência. Ele mostra quais arquivos foram modificados, quais são novos e ainda não estão sendo rastreados pelo Git, e quais já estão prontos para virar um commit. Rode git status sempre que estiver em dúvida sobre o estado do seu projeto — nunca custa nada rodar ele de novo. 

git status
# Saída típica:
#   modificado:   src/app.js
#   não rastreado: src/novo-arquivo.js

git add: escolhendo o que vai para a próxima foto

O git add move arquivos da "bagunça" para a "caixa de pronto para guardar" (a chamada staging area, ou área de preparação). Isso permite escolher exatamente quais mudanças vão entrar no próximo commit, mesmo que você tenha mexido em vários arquivos diferentes por motivos diferentes. 

git add src/app.js        # adiciona um arquivo específico
git add .                  # adiciona todos os arquivos modificados na pasta atual
Dica Usar git add . o tempo todo é tentador, mas rodar git status antes evita surpresas — como adicionar sem querer um arquivo de configuração local ou uma pasta de dependências que não deveria ir para o repositório. Vamos falar do arquivo .gitignore, que evita esse problema, na última lição desta trilha.

git commit: tirando a foto

Depois de dar add nos arquivos certos, o git commit transforma o que está na área de preparação num commit de verdade — permanente no histórico do repositório. Toda vez, é obrigatório escrever uma mensagem descrevendo o que foi feito, usando a flag -m. 

git commit -m "Adiciona validação de e-mail no formulário de cadastro"

Depois desse comando, aquela "fotografia" fica registrada para sempre no histórico local do repositório, com um identificador único, a data, o autor e a mensagem que você escreveu.

git push: enviando os commits para o repositório remoto

Até aqui, tudo aconteceu só no seu computador. O git push envia os commits que você criou localmente para o repositório remoto (por exemplo, no GitHub), para que fiquem salvos na nuvem e visíveis para o resto da equipe. 

git push origin main
# "origin" é o apelido do repositório remoto
# "main" é o nome da branch (linha do tempo) que está sendo enviada

git pull: trazendo o que outras pessoas enviaram

O oposto do push. O git pull busca os commits novos que existem no repositório remoto e os traz para o seu repositório local, mantendo sua cópia atualizada com o trabalho de outras pessoas. 

git pull origin main
Dica Um hábito saudável é rodar git pull antes de começar a trabalhar e antes de dar git push, para reduzir a chance de conflitos (assunto da próxima lição).

git log: consultando o álbum de fotos

Quer ver o histórico de commits de um projeto? O git log lista todos eles, do mais recente para o mais antigo, com autor, data, identificador e mensagem. 

git log
# commit a1b2c3d4...
# Author: Maria Silva <maria@email.com>
# Date:   Qui Jul 24 10:15:00 2026
#
#     Adiciona validação de e-mail no formulário de cadastro

Uma versão mais compacta e visual, ótima para o dia a dia, é: 

git log --oneline --graph --all

Juntando tudo: o ciclo do dia a dia

Na prática, o fluxo mais comum de trabalho, repetido várias vezes por dia, costuma ser assim: 

git pull origin main         # traz o que mudou
# ... você edita arquivos ...
git status                    # confere o que mudou
git add .                     # prepara as mudanças
git commit -m "..."           # registra o commit
git push origin main          # envia para o remoto
Atenção O git commit só registra o que passou pelo git add antes. É um erro comum achar que "editou o arquivo" já é suficiente — se você esquecer o add, aquele arquivo simplesmente não entra no commit, mesmo que a mudança já esteja salva no seu editor de código.

Resumo

  • git init cria um repositório novo; git clone copia um que já existe.
  • git status mostra o que mudou e o que está pronto para virar commit.
  • git add prepara arquivos; git commit -m "..." registra a mudança no histórico.
  • git push envia commits locais para o remoto; git pull traz commits do remoto.
  • git log (ou git log --oneline --graph --all) mostra o histórico de commits.
